Are .chat/articles_cache *.trunk, *.json, and *.md still needed?

Research for prompts/sqlite_bm25.prompt. Corpus inspected: 117 learned articles, 4,134 trunks, SQLite FTS5 BM25 index at .chat/articles_cache/bm25_index_fts.db.

Short answer: No, you cannot delete them all. The SQLite database is a rebuildable search index, not a copy of the learned articles. It stores only normalized tokens, not the original trunk text, titles, URLs, or paragraphs. Deleting every .trunk and .json file destroys the learned corpus and breaks server startup. The .md files, however, are write-only human-readable exports: no code reads them, so the .md files alone can be deleted safely.

What actually uses each file

File Count / size Role at runtime Can it be deleted?
news_<id>.<n>.trunk 4,134 files, ≈16 MB The learned article's original text, one paragraph per trunk. These are the documents that are ranked, passed to the answer model, and re-indexed by SQLite when they change. No. Required. Without them there is no readable corpus left (the FTS table only holds lowercased/normalized tokens), and startup has nothing to index.
news_<id>.json 117 files, ≈1.2 MB Article metadata: title, link, source, section, published, summary, paragraphs, and images. Read by /api/news_status, /api/news_item, and source labels/links; also used to decide whether an item is "learned". No. Required by the news/wikivoyage UI and by the learned-state checks. The DB has no copy of this metadata.
news_<id>.title 117 files, ≈468 KB Duplicate of the JSON title. The web server reads titles from .json, but chat.py's video_title() falls back to .chat/articles_cache/<id>.title for learned articles. Technically yes, but not recommended. The web UI still works, but CLI labels for learned news would degrade to raw ids. It is only 468 KB; keep it.
news_<id>.md 117 files, ≈1.1 MB A human-readable Markdown copy written at learn time. It is never read by Python, the server, the browser, or PHP. Yes. Safe to delete. This is the only category that is pure output.
bm25_index_fts.db (+ -wal/-shm) ≈51 MB + ≈5 MB WAL The on-disk FTS5 BM25 index. Stores tokenized documents and per-document signatures, and is rebuilt incrementally from the trunks. Yes, it is a cache. Delete it only while the server is stopped; it will be rebuilt from the trunks (the existing cold build took about 5.8 s for 26k trunks). Deleting it does not delete knowledge, but it is the opposite of what freeing space by deleting trunks would do.

Why the database cannot replace the trunks

sqlite_bm25.py is explicit about what it stores. The FTS5 content column receives " ".join(tokens), where the tokens come from chat._bm25_document_tokens() → tokenize(...). That pipeline lowercases, normalizes plurals, and canonicalizes times; punctuation and original casing are gone. The database is a retrieval index, and it is described in its own module docstring as an index that is "incremental" and rebuilt from trunk files. 

# sqlite_bm25.py (sync)
pending.append((doc_id, key, " ".join(tokens), mtime_ns, size))

# chat.py (what is tokenized)
def _bm25_document_tokens(chunk: Chunk) -> list[str]:
    text = paragraph_text(chunk)
    title = video_title(chunk.video_id)
    heading = getattr(chunk, "section_heading", "")
    parts = [part for part in (title, heading, text) if part]
    return tokenize("\n".join(parts))

The answer path calls paragraph_text(chunk), which reads chunk.trunk_path. Likewise, chat.load_news_chunks() discovers the corpus by globbing ARTICLES_DIR/*.trunk. If the trunks disappear, no chunks are loaded, chat.load_all_chunks() exits with "No learned trunks found…", and the server cannot construct its ChatState.

Code evidence (read paths)

  • Trunks are loaded as the corpus: chat.py → load_news_chunks() sorts ARTICLES_DIR.glob("*.trunk") and builds Chunk objects from them.
  • Trunks are the prompt text: chat.paragraph_text() reads chunk.trunk_path.read_text(); the answer model receives this, not tokens from SQLite.
  • Trunks drive incremental indexing: _bm25_sync_entries() compares each trunk's mtime_ns/size and only tokenizes new or changed files.
  • JSON is the metadata store: app/chat_server.py → _read_news_meta(), news_is_learned(), news_title(), news_link(), /api/news_status, and /api/news_item.
  • Markdown is write-only: learn_news_article() writes NEWS_CACHE_DIR / f"{news_id}.md"; a repository-wide search finds no read of that file. The only .md mention in the server outside comments is the write_text(...) call itself.
  • Titles are a fallback: chat.video_title() reads ARTICLES_DIR/<id>.title after looking in the YouTube transcript directory.
  • SQLite is pruned when trunks vanish: server startup calls chat.get_bm25_index(state.chunks, prune=True). Once the trunk files are gone, the corresponding DB rows are considered stale and pruned, so an "index-only" cache shrinks to nothing on the next start.

What you can safely clean up

Safe: remove the human-readable Markdown exports (117 files, ≈1.1 MB):

find .chat/articles_cache -maxdepth 1 -name 'news_*.md' -delete

Nothing in the application reads these files. They can be regenerated from the corresponding .json if you ever want them back.

Safe with the server stopped: remove the search index to force a clean rebuild (≈56 MB):

# stop app/chat_server.py first
rm .chat/articles_cache/bm25_index_fts.db .chat/articles_cache/bm25_index_fts.db-wal .chat/articles_cache/bm25_index_fts.db-shm

It is a derived cache; the next startup rebuilds it from the trunks. Do not do this expecting to save disk permanently, because it comes right back.

Do not delete: news_*.trunk or news_*.json.

Deleting the trunks removes the original learned text used for prompts and forces the SQLite rows to be pruned; deleting the JSON removes titles, URLs, summaries, paragraphs, images, and the learned-state marker. The database contains neither. The result would be an empty/broken corpus, not a leaner one.

Recommendation

  1. Keep *.trunk and *.json — they are the source of truth for learned articles.
  2. Keep *.title — small, and still used as the CLI title fallback.
  3. Delete only *.md if you want a small, safe cleanup; it is a write-only convenience copy.
  4. Treat bm25_index_fts.db as a rebuildable cache, not as storage.
  5. Long term: if disk usage matters, the effective lever is the number/size of learned articles and the SQLite DB, not the tiny Markdown exports. Trunk files (≈16 MB) are the knowledge itself and should not be treated as disposable.

Conclusion

The FTS5 migration moved the scoring structure to disk; it did not make the learned article files redundant. .trunk files are the text the chatbot answers from, .json files are the article metadata the UI needs, and .md is a write-only export. Therefore: you can delete all the .md files, but you cannot delete the .trunk or .json files without destroying the learned-article corpus.
