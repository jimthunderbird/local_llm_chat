Are .chat/articles_cache *.trunk, *.json, and *.md still needed?

Research for prompts/sqlite_bm25.prompt. Corpus inspected: 117 learned articles, 4,134 trunks, SQLite FTS5 BM25 index at .chat/articles_cache/bm25_index_fts.db.

Short answer: No, you cannot delete them all. The SQLite database is a rebuildable search index, not a copy of the learned articles. It stores only normalized tokens, not the original trunk text, titles, URLs, or paragraphs. Deleting every .trunk and .json file destroys the learned corpus and breaks server startup. The .md files, however, are write-only human-readable exports: no code reads them, so the .md files alone can be deleted safely.

What actually uses each file

File Count / size Role at runtime Can it be deleted?
news_<id>.<n>.trunk 4,134 files, ≈16 MB The learned article's original text, one paragraph per trunk. These are the documents that are ranked, passed to the answer model, and re-indexed by SQLite when they change. No. Required. Without them there is no readable corpus left (the FTS table only holds lowercased/normalized tokens), and startup has nothing to index.
news_<id>.json 117 files, ≈1.2 MB Article metadata: title, link, source, section, published, summary, paragraphs, and images. Read by /api/news_status, /api/news_item, and source labels/links; also used to decide whether an item is "learned". No. Required by the news/wikivoyage UI and by the learned-state checks. The DB has no copy of this metadata.
news_<id>.title 117 files, ≈468 KB Duplicate of the JSON title. The web server reads titles from .json, but chat.py's video_title() falls back to .chat/articles_cache/<id>.title for learned articles. Technically yes, but not recommended. The web UI still works, but CLI labels for learned news would degrade to raw ids. It is only 468 KB; keep it.
news_<id>.md 117 files, ≈1.1 MB A human-readable Markdown copy written at learn time. It is never read by Python, the server, the browser, or PHP. Yes. Safe to delete. This is the only category that is pure output.
bm25_index_fts.db (+ -wal/-shm) ≈51 MB + ≈5 MB WAL The on-disk FTS5 BM25 index. Stores tokenized documents and per-document signatures, and is rebuilt incrementally from the trunks. Yes, it is a cache. Delete it only while the server is stopped; it will be rebuilt from the trunks (the existing cold build took about 5.8 s for 26k trunks). Deleting it does not delete knowledge, but it is the opposite of what freeing space by deleting trunks would do.

Why the database cannot replace the trunks

sqlite_bm25.py is explicit about what it stores. The FTS5 content column receives " ".join(tokens), where the tokens come from chat._bm25_document_tokens() → tokenize(...). That pipeline lowercases, normalizes plurals, and canonicalizes times; punctuation and original casing are gone. The database is a retrieval index, and it is described in its own module docstring as an index that is "incremental" and rebuilt from trunk files. 

# sqlite_bm25.py (sync)
pending.append((doc_id, key, " ".join(tokens), mtime_ns, size))

# chat.py (what is tokenized)
def _bm25_document_tokens(chunk: Chunk) -> list[str]:
    text = paragraph_text(chunk)
    title = video_title(chunk.video_id)
    heading = getattr(chunk, "section_heading", "")
    parts = [part for part in (title, heading, text) if part]
    return tokenize("\n".join(parts))

The answer path calls paragraph_text(chunk), which reads chunk.trunk_path. Likewise, chat.load_news_chunks() discovers the corpus by globbing ARTICLES_DIR/*.trunk. If the trunks disappear, no chunks are loaded, chat.load_all_chunks() exits with "No learned trunks found…", and the server cannot construct its ChatState.

Code evidence (read paths)

  • Trunks are loaded as the corpus: chat.py → load_news_chunks() sorts ARTICLES_DIR.glob("*.trunk") and builds Chunk objects from them.
  • Trunks are the prompt text: chat.paragraph_text() reads chunk.trunk_path.read_text(); the answer model receives this, not tokens from SQLite.
  • Trunks drive incremental indexing: _bm25_sync_entries() compares each trunk's mtime_ns/size and only tokenizes new or changed files.
  • JSON is the metadata store: app/chat_server.py → _read_news_meta(), news_is_learned(), news_title(), news_link(), /api/news_status, and /api/news_item.
  • Markdown is write-only: learn_news_article() writes NEWS_CACHE_DIR / f"{news_id}.md"; a repository-wide search finds no read of that file. The only .md mention in the server outside comments is the write_text(...) call itself.
  • Titles are a fallback: chat.video_title() reads ARTICLES_DIR/<id>.title after looking in the YouTube transcript directory.
  • SQLite is pruned when trunks vanish: server startup calls chat.get_bm25_index(state.chunks, prune=True). Once the trunk files are gone, the corresponding DB rows are considered stale and pruned, so an "index-only" cache shrinks to nothing on the next start.

What you can safely clean up

Safe: remove the human-readable Markdown exports (117 files, ≈1.1 MB):

find .chat/articles_cache -maxdepth 1 -name 'news_*.md' -delete

Nothing in the application reads these files. They can be regenerated from the corresponding .json if you ever want them back.

Safe with the server stopped: remove the search index to force a clean rebuild (≈56 MB):

# stop app/chat_server.py first
rm .chat/articles_cache/bm25_index_fts.db .chat/articles_cache/bm25_index_fts.db-wal .chat/articles_cache/bm25_index_fts.db-shm

It is a derived cache; the next startup rebuilds it from the trunks. Do not do this expecting to save disk permanently, because it comes right back.

Do not delete: news_*.trunk or news_*.json.

Deleting the trunks removes the original learned text used for prompts and forces the SQLite rows to be pruned; deleting the JSON removes titles, URLs, summaries, paragraphs, images, and the learned-state marker. The database contains neither. The result would be an empty/broken corpus, not a leaner one.

Recommendation

  1. Keep *.trunk and *.json — they are the source of truth for learned articles.
  2. Keep *.title — small, and still used as the CLI title fallback.
  3. Delete only *.md if you want a small, safe cleanup; it is a write-only convenience copy.
  4. Treat bm25_index_fts.db as a rebuildable cache, not as storage.
  5. Long term: if disk usage matters, the effective lever is the number/size of learned articles and the SQLite DB, not the tiny Markdown exports. Trunk files (≈16 MB) are the knowledge itself and should not be treated as disposable.

Conclusion

The FTS5 migration moved the scoring structure to disk; it did not make the learned article files redundant. .trunk files are the text the chatbot answers from, .json files are the article metadata the UI needs, and .md is a write-only export. Therefore: you can delete all the .md files, but you cannot delete the .trunk or .json files without destroying the learned-article corpus.

Can SQLite FTS5 BM25 retrieval be made 50% faster?

Follow-up research for prompts/sqlite_bm25.prompt. Measured 2026-11-11 on the production corpus: 26,202 global trunks (591 videos + 120 learned articles), FTS5 database .chat/articles_cache/bm25_index_fts.db (138 MB, 125,511 rows across one global and four stale scoped tables). Timings are the best of five warm runs in the same process; the goal was to keep SQLite FTS5 + BM25 and cut retrieval time by at least 50%.

Answer: yes, comfortably. Pruning stopwords from the FTS5 MATCH expression and returning only the top candidates reduced the complete top_chunks() retrieval stage from 418 ms to 77.5 ms over eight representative questions (5.4× faster, 81.5% less time). The raw get_scores() call alone dropped from 264.8 ms to 40.2 ms (6.6×). FTS5 optimize contributes another ~29% on top of that, and dropping the stale scoped tables shrinks the database from 138 MB to 34 MB. The speedup target is met by stopword pruning alone; the other changes make it larger and reduce disk/cache pressure.

Benchmark setup

The benchmark used the real chat.load_all_chunks(), chat.get_bm25_index(), chat.top_chunks(), and sqlite_bm25.SQLiteBM25 code paths (Ollama was not called). Queries: 

what can i eat in Izumo
where is nijo market
what are all levels of wagyu
can i do left turn on red light
tell me about the history of kyoto
did terrence tao write a new book
how does the nvidia ai chip work
what is the best time to visit japan

top_chunks(..., limit=100) was chosen because it includes the normal 20-result default, the /depth path, and the iterative /article path. Scores were compared against the unmodified implementation, and the selected top-10 paragraphs were inspected for relevance as well as counted for overlap.

Where the time goes

The current query is an OR of every question token, repeated to weight question words twice, plus fuzzy corrections, acronym expansions, and model expansion terms. Function words such as what, is, the, in, and me therefore appear as full BM25 terms. On this corpus that makes almost the entire 26,202-document global table match:

QuestionDocuments matched by current MATCH
what can i eat in Izumo23,422 / 26,202
where is nijo market18,770 / 26,202
what are all levels of wagyu22,411 / 26,202
can i do left turn on red light21,531 / 26,202
tell me about the history of kyoto24,881 / 26,202
did terrence tao write a new book21,547 / 26,202
how does the nvidia ai chip work24,886 / 26,202
what is the best time to visit japan25,857 / 26,202

FTS5 must score, sort, and return every one of those rows. Python then builds a 26,202-entry score map and an almost-as-large ranked list, only for _select_auto_chunks() to look at the first 50 candidates. The query plan shows the expected shape: 

SCAN chunk_index_<hash> VIRTUAL TABLE INDEX 0:M1
SEARCH d USING INDEX sqlite_autoindex_chunk_documents_1
       (corpus_key=? AND doc_id=?)

In other words, the join is cheap; the cost is that the MATCH selects 70-99% of the corpus and every selected row is materialized in Python. Function words add almost no ranking signal because their IDF is tiny, but they do add a large candidate set.

1. Prune stopwords from the MATCH expression (largest win)

Keep the original token list for fuzzy correction, entity detection, acronym expansion, and expansion validation. Only the list handed to get_scores() is filtered. If filtering leaves at least one content word, use the filtered list; otherwise fall back to the original list so a question made only of function words still searches. 

search_tokens = query_tokens
content_tokens = [
    token for token in search_tokens
    if token not in FUZZY_ANCHOR_STOPWORDS
]
if content_tokens:
    search_tokens = content_tokens

scores = index.bm25.get_scores(
    search_tokens, index.chunk_keys, limit=500
)

Repeated content tokens are preserved, so the existing question-word weighting and FTS5 phrase-weight behavior are unchanged. Measured over the eight questions:

Implementationget_scores totalTime reduction
Current (all question tokens, all rows)264.8 ms-
Stopwords pruned, top 500 rows40.2 ms84.8% (6.6×)
Same, on an optimized/compacted database27.5 ms89.6% (9.6×)

A smaller, classic stopword list (keeping new, latest, and current) still gives 443.5 ms → 91.1 ms end-to-end on top_chunks(), a 79.5% reduction. This is the safer list for news-like questions where those time words can be topical.

2. Return only the top candidates

get_scores() currently returns a list aligned with all chunk_keys. Only candidates near the top can ever be selected: AUTO_CANDIDATE_LIMIT = 50, the default depth is 20, and the iterative article path requests a small candidate pool. Add a limit to the SQL query: 

SELECT d.chunk_key, bm25("chunk_index_<hash>")
FROM "chunk_index_<hash>"
JOIN chunk_documents AS d
  ON d.corpus_key = ?
 AND d.doc_id = "chunk_index_<hash>".rowid
WHERE "chunk_index_<hash>" MATCH ?
ORDER BY bm25("chunk_index_<hash>")
LIMIT ?;

A limit of 500 is ample (10× the adaptive candidate cap, 25× the default depth) and bounds the Python-side map and ranked list. Do not use ORDER BY rank: on this SQLite build it measured slower than ORDER BY bm25(...). For a further small gain, select rowid only and translate doc_id -> chunk_key from a cached dictionary loaded at index build time; the join added about 33% in isolation (27.7 ms vs 41.5 ms over the eight queries).

3. Run FTS5 optimize

FTS5 keeps several b-tree segments after incremental inserts. Running the special optimize command merges them into one segment, which reduces MATCH and bm25() work: 

INSERT INTO "chunk_index_<hash>"("chunk_index_<hash>")
VALUES('optimize');

On a global-only copy this took about 0.2 s and cut the eight-query baseline from 275.0 ms to 194.9 ms (29%). Run it at server startup after syncing, and after a bulk learn operation (video or article); do not run it inside a question request. It is a write operation, so it should happen on the learning or startup thread.

4. Drop stale scopes and VACUUM

The database held five corpora: global with 26,202 documents plus four stale scope_* tables with about 24,800 documents each. Those scopes are rebuildable and already dropped by drop_transient_corpora() at startup, but the freed pages are not returned to the filesystem. Dropping the stale tables and running VACUUM took the copy from 138 MB to 34 MB without changing the global rows. A smaller file means more of the index stays resident in the OS page cache and less WAL/checkpoint work. 

# with the server stopped, or on a maintenance thread
DROP TABLE IF EXISTS "chunk_index_<stale hash>";
DROP TABLE IF EXISTS "chunk_vocab_<stale hash>";
DELETE FROM chunk_documents WHERE corpus_key LIKE 'scope_%';
DELETE FROM corpora WHERE corpus_key LIKE 'scope_%';
VACUUM;  -- rewrites the file; needs temporary free space

VACUUM alone did not speed up the global query in the warm-cache benchmark; it is a storage/cache-residency improvement, not a query-plan improvement. Pair it with optimize for the query win.

Quality check

Dropping stopwords changes the candidate set, so this is not a byte-identical drop-in. Spot checks show the change is usually an improvement because function-word-only documents disappear:

  • Wagyu: the top 10 results are effectively identical; the same ten-level Wagyu video dominates both rankings.
  • Kyoto history: the current top 10 is mostly generic AI-history paragraphs that happen to contain history and the. The filtered ranking replaces them with Kyoto travel paragraphs, including the Wikivoyage Japan article and the “Little Kyoto of Iyo” segment.
  • Nijo Market: all 50 current top results are preserved; 97 of the top 100 remain.

For queries whose relevant set is large, the top-50 overlap with the current implementation was 40-50/50. The exceptions are cases where the current top-50 is filled with function-word-only matches; there the new ranking is the more relevant one. Run the existing evaluation questions before rollout and keep the classic-stopword fallback if any regression appears.

What did not help

  • PRAGMA mmap_size=268435456: no measurable change on warm queries (27.7 ms either way).
  • PRAGMA cache_size=-65536: no improvement; slightly slower in this benchmark.
  • ORDER BY rank instead of ORDER BY bm25(...): about 40% slower for the limited query (39.0 ms vs 27.7 ms over the eight queries).
  • A subquery that applies LIMIT before joining chunk_documents: slower (52.2 ms) because SQLite materialized the subquery. A plain top-K join or a cached doc_id -> chunk_key map is better.
  • VACUUM alone: storage win only, no warm-query win.

Recommended implementation order

  1. Stopword-prune the BM25 query. In top_chunks() (or inside get_scores() with a stopword argument), filter the weighted token list, fall back to the unfiltered list when nothing remains, and keep the original tokens for fuzzy/entity/acronym logic. This alone exceeds the 50% target.
  2. Add a top-K limit to get_scores(). Return only rows that can be selected (500 is plenty; make it a constant, not a per-call allocation). Optionally return a {chunk_key: score} dict so callers do not build a 26,202-element aligned list.
  3. Replace the join with a cached id map if more speed is needed: load doc_id -> chunk_key once with the index metadata and select rowid, bm25(...) in the hot query.
  4. Run FTS5 optimize at startup after sync()/prune(), and after bulk learning. Guard it with a flag so concurrent readers use WAL and do not block.
  5. VACUUM after dropping transient scopes when the server is idle (or on a maintenance command), so the file shrinks from the stale 100k+ scope rows. Do not run it per request.
  6. Keep the database path and schema unchanged. All of the above are query-construction and maintenance changes; SQLite FTS5 and its native BM25 remain the only ranking engine.

Expected impact and caveats

  • Retrieval stage: 5.4× faster end-to-end in the benchmark (81.5% less time), versus the 50% target.
  • Full answer latency: the retrieval stage is tens of milliseconds while Ollama prefill/generation is seconds. These changes cannot by themselves halve the wall-clock time to a streamed answer; they remove 30-70 ms of avoidable work and make the BM25 stage negligible. If the perceived slowdown is in answer generation, measure TTFT before and after and tune the model/context path separately.
  • Quality: stopword removal is a standard BM25 optimization, but it changes the candidate set. Keep the fallback and run the evaluation questions; do not combine it with a lower AUTO_CANDIDATE_LIMIT without re-checking recall.
  • Maintenance: optimize and VACUUM are writes. Schedule them at startup or during learning, never on the question path. Back up the DB before the first VACUUM; it needs temporary free space roughly equal to the database size.

Validation checklist

  1. Run the eight benchmark questions plus the existing Nijo Market, Izumo food, wagyu, IDP, Terence Tao, and Kyoto questions through top_chunks(); assert the expected source paragraph is still in the top 20.
  2. Compare top-10 source paragraphs before and after for each evaluation question; flag any answer-source regression.
  3. Measure top_chunks() p50/p95 after a warm index rebuild; expect the 5× reduction shown here.
  4. Confirm the FTS5 DB is one global table plus temporary scopes, and that drop_transient_corpora() plus VACUUM leave the file near 34 MB for the current corpus.
  5. Run py_compile on chat.py, sqlite_bm25.py, and app/chat_server.py, then start the server and ask one live question to verify the streaming path.

Bottom line: the BM25 stage is not slow because SQLite FTS5 is slow; it is slow because the query asks FTS5 to score almost every document for a handful of function words and then materializes all of those rows in Python. Stopword pruning plus a top-K SQL limit is the 50%+ fix; optimize and scope compaction are the maintenance follow-ups.
