Deep research mode: beyond BM25 retrieval depth

Research report for prompts/deep_research_mode.prompt. Measured on this machine on 2026-11-13 against the live global corpus. Report file: research/deep_research_mode.html.

Short answer: no, increasing BM25 depth is not the way to get deep research. Depth is a top-k knob, not a research strategy. In this repo the default DEFAULT_DEPTH is 12. Raising it to 50 or 100 does not make BM25 slower in any meaningful way (warm queries stay around 10–20 ms), but it does make the prompt much larger. The answer model runs with an 8,192-token context window, and Ollama silently drops the beginning of an oversized prompt. That beginning contains the answer instructions and the highest-ranked evidence. In a controlled test, depth 100 produced a worse answer than depth 12 or 50 because the prompt was truncated to 4,098 evaluated tokens. Deep research needs planning, sub-question retrieval, an evidence ledger, gap-driven rounds, section-wise synthesis, and verification — not a larger single-shot context.

1. Executive answer

The question was: “I would really like doing deep research of any topic … I want to really achieve deep research result. Should I increase the depth of the BM25 retrieval? Or do we have a better approach?”

Increase depth only within a small, evidence-budgeted range. The better approach is a deep-research loop that uses depth as one low-level tool:

  1. Plan the question into a small set of sub-questions and state what kind of evidence would answer each one.
  2. Retrieve per sub-question with several targeted queries, not one global top-100 query.
  3. Keep an evidence ledger with source id, title, URL, date, excerpt, score, and which sub-question it supports.
  4. Check gaps and contradictions after each round, then retrieve only for the missing pieces.
  5. Synthesize section by section from the ledger, keeping every model call inside the 8k window.
  6. Verify claims and cite sources, and state explicitly what the corpus does not establish.

For normal chat, keep DEFAULT_DEPTH = 12. For list/long-form questions, 25–50 is usually enough. Do not use 100+ as a substitute for research: it increases token count, redundancy, and truncation risk while adding little new evidence.

2. What “deep research” actually means

“Deep research” is not a synonym for “retrieve more chunks.” Across the 2025 literature and production systems, it is a multi-stage, iterative workflow. The survey Deep Research: A Survey of Autonomous Research Agents (Zhang et al., 2025) describes four core stages: planning, question developing, web exploration, and report generation. The systematic survey by Shi et al. (2025) describes four components in the same spirit: query planning, information acquisition, memory management, and answer generation.

OpenAI’s Deep Research (Feb 2025) is described as a browsing-and-reasoning agent that “finds, analyzes, and synthesizes hundreds of online sources to create a comprehensive report,” takes 5–30 minutes, and cites specific passages. Anthropic’s Research system (Jun 2025) uses an orchestrator-worker design: a lead agent plans, spawns parallel subagents with separate context windows, and a citation agent attaches claims to sources. Neither system is “BM25 with a larger top_k.”

2.1 The loop that makes research different from RAG

Plan → decompose the question into sub-goals; decide source types, effort, and stopping criteria.
Develop questions → turn each sub-goal into several precise, diverse queries, including entity aliases, synonyms, dates, and counter-hypotheses.
Explore → retrieve from the corpus (and optionally the web or official docs), filter, deduplicate, and record evidence.
Reflect → which sub-questions are answered, partial, missing, or contradictory? What new query would close the gap?
Remember → store findings in an external ledger so the plan and evidence survive context limits; do not rely on one prompt to hold everything.
Synthesize → write a structured report section by section, with a citation contract.
Verify → check each claim against its cited evidence; mark unsupported claims, conflicts, and unknowns.

The key idea is token scaling through iteration and decomposition, not token stuffing. Anthropic reports that a multi-agent research system with a lead agent and parallel subagents outperformed a single agent by 90.2% on their internal research eval for breadth-first queries. They also report that token usage alone explained 80% of performance variance on BrowseComp, and that multi-agent systems use about 15× more tokens than chat. That is the trade: spend more tokens across focused contexts, not more tokens in one oversized context.

2.2 What it is not

  • It is not “set /depth 100.” That only changes one BM25 slice.
  • It is not “stuff the whole corpus into the prompt.” The answer model has a fixed 8,192-token window; oversized prompts are truncated.
  • It is not “let the model free-associate from memory.” A research report must be grounded in an evidence ledger and citations.
  • It is not “always more sources.” Source quality, independence, recency, and relevance matter more than raw count.

The iterative loop already does something research-like: it retrieves a few paragraphs, checks sufficiency with a small model, and searches again with missing terms. It is a useful foundation. It is not yet a full research agent: it has no explicit plan, no per-sub-question ledger, no contradiction pass, and its evidence budget exceeds the answer window.

Averages hide the important outliers. For “what are all levels of wagyu,” depth 12 used ~1,453 tokens, depth 50 ~5,922, depth 100 ~11,331, and depth 200 ~20,262. For “list me all airports in japan,” depth 100 used ~10,033 tokens and depth 200 ~21,844. Warm BM25 itself stayed under 70 ms in every case; the first query paid a one-time ~1.7 s index/database warm-up cost.

Depth is cheap for BM25 and expensive for the answer model. The SQLite FTS5 index returns a few hundred scored candidates quickly. The cost is what happens next: more chunks mean a longer prompt, more prefill, more redundancy, and a higher chance of crossing the 8,192-token window. Increasing depth from 12 to 200 multiplied average context size by about 7× while adding few genuinely new sources.

3.4 The context-window cliff

The answer model is called with num_ctx = 8192. The prompt is built as: instructions and rules first, then the <context> blocks, then the target question at the end. When the prompt is too long, Ollama/llama.cpp truncates it. Empirically, the truncation dropped the beginning of the prompt — exactly where the instructions and the highest-ranked evidence live.

I tested this directly with the production answer model, ornith-1.5:35b, at num_ctx = 8192:

  1. Put a secret code at the beginning of a prompt, then ~12k estimated tokens of harmless filler, then ask for the code.
  2. Ollama reported prompt_eval_count = 4098, not ~12k. The model answered: “I don't have access to any secret code.”
  3. This proves a large prefix was dropped before inference. The same mechanics apply to a long RAG prompt: instructions and the first (best) chunks can disappear.

3.5 A controlled answer-quality experiment

Question: “what are all levels of wagyu”. Same corpus, same model (ornith-1.5:35b), same prompt template, only depth changed.

DepthEstimated contextPrompt tokens evaluatedResult
12 1,476 1,764 Good. Listed yield grades A/B/C, quality grades 1–5, combined A1–A5, BMS 1–12, and flagged the BMS discrepancy.
50 6,150 6,572 Best. Added B5/C5, USDA Select/Choice/Prime, brand-beef requirements, and kept the discrepancy note.
100 11,495 4,098 Worse. Said there was “no single comprehensive list,” cited “chunks 75, 81, 89” (violating the no-chunk-citation rule), and lost the core A/B/C + 1–5 grading system.

This is the central empirical finding: depth 100 was worse than depth 12 because the prompt crossed the window and the front of the prompt was discarded. Depth 50 was the sweet spot for this list question; depth 12 was already adequate and much cheaper.

3.6 Entity focus can cap depth

Depth is also not guaranteed to add anything. For the question “how many affairs jensen huang might actually have,” depths 12, 25, 50, 100, and 200 all returned the same 10 chunks. The entity-focus and topic filters in top_chunks() kept only the chunks that actually matched the named entity; there were no additional positive matches to expose. Raising the limit could not create evidence that the corpus did not contain. This is a feature, not a bug — but it means “increase depth” can be a no-op on exactly the questions where users expect it to help.

3.7 Current iterative budgets exceed the answer window

Budget mismatch: chat.ANSWER_NUM_CTX = 8192, but YOUTUBE_ITERATIVE_EVIDENCE_TOKENS and ARTICLE_ITERATIVE_EVIDENCE_TOKENS are both 16000. The iterative loop can therefore gather roughly twice as much evidence as the model can attend to in one call. Unless the prompt is split into sections or the budget is reduced, the same truncation failure is possible even when the iterative logic “found enough” evidence.

Recommended fix: either (a) cap each synthesis prompt at about 8192 − 1024 output reserve − 512 template/instructions ≈ 6,500 tokens, or (b) raise num_ctx to 16k/32k and re-measure memory, prefill, and TTFT. Option (a) is cheaper and safer; option (b) increases the KV-cache footprint and prefill cost. In either case, add a hard assertion or log line when the prompt exceeds the budget, and trim the lowest-ranked chunks rather than letting the runtime silently drop the highest-ranked ones.

4. Why “increase depth” is the wrong lever

4.1 What depth buys

  • More candidates for a single lexical query. This can help recall when the query is broad and the relevant evidence is spread out.
  • A better chance that a specific fact appears somewhere in the prompt, if the corpus contains it and BM25 ranks it above the cutoff.
  • More source diversity, up to the point where the per-source cap and near-duplicate filter kick in.

4.2 What depth costs

  • Context growth is linear. 12 → 50 roughly tripled average context; 12 → 200 roughly septupled it. The 8k window does not grow.
  • Truncation risk becomes real. The wagyu depth-100 case crossed the window and lost the instructions and best evidence. The answer got worse, not better.
  • Redundancy. At depth 200, wagyu used 23 unique sources for 200 chunks (~8.7 chunks per source); airports used 51 sources for 200 chunks. Many chunks repeat the same point in different words.
  • Relevance decay. Median BM25 scores fell steadily with depth: for the jensen timeline question, median 31.9 at depth 12, 30.8 at 25, 29.2 at 50, 28.5 at 100, and the tail included weak matches. More depth means more low-signal text competing for attention.
  • Model attention limits. Even within a window, models use middle context less reliably than the beginning and end (“lost in the middle”). Stuffing more text into the middle is not the same as giving the model more useful evidence.
  • Cost and latency. BM25 is cheap, but prefill and generation are not. A larger prompt costs more time and compute on every question, and it makes caching less effective.

4.3 The right mental model

KnobWhat it controlsGood useBad use
/depth How many BM25 candidates one query returns 8–12 for direct facts; 25–50 for a broad list or a long-form request; always under the token budget 100–200 as a substitute for planning or multiple queries
Query expansion Synonyms, aliases, acronyms, entity spellings Improve recall for a known topic Expect it to invent missing evidence
Iterative retrieval Multiple focused rounds with a sufficiency check Close a specific gap; cover a multi-part question Loop forever; exceed the prompt budget

5. A better approach: a bounded /research loop

The proposal below is designed for this codebase: SQLite FTS5 BM25, a global corpus of learned articles and transcripts, a 1.7B helper model for short structured calls, and ornith-1.5:35b for writing. It is research-only here; no implementation is included.

5.2 Phase 0 — intent and scope

Classify the request before retrieving. The class determines the effort budget:

IntentExamplesPlan shapeBudget
Direct fact“what time does Nijo market open?”1 sub-question, 1–2 queriesDepth 8–12, 1 round
Timeline / recency“timeline of the Jensen Huang scandal”3–5 time-bounded sub-questionsDepth 25–50, 2–3 rounds, newest-first
Comparison“compare Dr. Knott and Dr. Pletcher”One sub-question per entity + one comparisonDepth 12 per entity, 2 rounds
Enumeration“list all airports in Japan”Coverage-oriented sub-questions; dedupe entitiesDepth 25–50 per region/category, 2–4 rounds

Speculation / private facts“how many affairs might Jensen Huang have?”Separate “reported,” “confirmed,” “speculated,” “unknown”Evidence-first, no invented count

The scope classifier should also decide whether the local corpus is the right source. If the question is about live market data, a private person’s private life, or a topic absent from the corpus, the correct output may be “the corpus cannot establish this” plus a list of what is reported. That is a successful research result, not a failure.

5.3 Phase 1 — plan and decompose

Use the small helper model with a strict JSON schema. Keep the plan small: 3–8 sub-questions is enough for most tasks. Each sub-question needs an id, text, type, priority, and the source types that could answer it. A sample schema: 

{
  "question": "original question",
  "intent": "timeline | comparison | enumeration | causal | open_ended | speculation",
  "subquestions": [
    {
      "id": "q1",
      "text": "What relationships/affairs have been publicly reported?",
      "type": "fact",
      "priority": 1,
      "source_types": ["news", "corpus"],
      "seed_queries": ["Jensen Huang affair", "Jensen Huang Alice Huang"]
    }
  ],
  "required_source_types": ["news", "corpus"],
  "stop_rules": {
    "max_rounds": 3,
    "max_evidence_tokens": 6000,
    "max_unique_sources": 30
  }
}

Useful model choices in this repo: chat.chat_helper_model() or chat.EXPANSION_MODEL (the LFM 1.7B helper) for planning, gap checks, and claim classification. Use ornith-1.5:35b only for the report writer and, if needed, for complex contradiction adjudication.

5.4 Phase 2 — per-subquestion retrieval and the evidence ledger

For each sub-question, generate several query variants:

  • the sub-question text itself;
  • entity aliases and acronym expansions (chat.acronym_expansion, chat.question_acronym_expansions);
  • query expansion from the helper model (chat.expand_query);
  • for temporal questions, explicit dates/years and “latest” variants (chat.question_is_time_sensitive, chat.normalize_time_expressions);
  • for comparisons, one query per entity plus a joint query;
  • for enumerations, category/region variants, then entity deduplication.

Run each variant with chat.top_chunks(query, chunks, limit=8..12), merge, filter with the existing small-model filter, and deduplicate by:

  • chunk key (video_id, index);
  • near-duplicate text (Jaccard, reuse NEAR_DUPLICATE_JACCARD);
  • source cap per video/article (reuse MAX_CHUNKS_PER_VIDEO).

Store each evidence item in a ledger. A practical schema: 

{
  "evidence_id": "E07",
  "chunk_key": "news_1098f902bbce314d.4",
  "source_id": "news_1098f902bbce314d",
  "title": "Jensen Huang resigns from Nvidia: Timeline ...",
  "url": "https://...",
  "published_at": "2026-11-11",
  "text": "full paragraph text",
  "excerpt": "the sentence(s) that matter",
  "bm25_score": 51.16,
  "subquestions": ["q1", "q2"],
  "stance": "supports | contradicts | context",
  "source_quality": "primary | major_outlet | aggregator | commentary",
  "notes": "NYT report cites five former Nvidia staff; neither party acknowledged"
}

Do not keep only the raw paragraph. Extract the minimal claim-bearing excerpt and keep the full text and URL for verification and citation. This is the “memory management” component the surveys describe: consolidate, index, update, and forget low-value evidence.

5.5 Phase 3 — gap-driven rounds

After each round, ask the small model (or use deterministic checks first):

  • Which sub-questions are answered, partial, or unanswered?
  • Which named entities, dates, numbers, or comparisons are still missing?
  • Do any sources contradict each other on a material fact?
  • Is the new evidence actually new, or is it a paraphrase of what we already have?

Reuse the existing helpers: _article_sufficiency_check(), _missing_search_terms(), and _evidence_covers_question(). The last one is a cheap fast path: if the evidence already contains every content word from the question, do not spend a model call. Stop when:

  • all high-priority sub-questions are answered; or
  • two consecutive rounds add less than ~10% new evidence; or
  • the evidence token budget is reached; or
  • the user-specified time/latency budget is reached.

Do not keep looping just because depth is available. A good research system stops with a clear “what remains unknown” section.

5.6 Phase 4 — section-wise synthesis

Do not put the entire ledger into one 8k prompt. Instead:

  1. Generate an outline from the plan and a compact index of evidence (claim + source id only, not full text).
  2. For each section, select the evidence that supports that section (typically 3–8 evidence items, ~1,500–3,500 tokens).
  3. Call the writer with a section-specific prompt, the selected evidence, the citation contract, and a short summary of already-written sections.
  4. Stream the section to the UI; keep the section text in the report ledger.
  5. At the end, generate the introduction and conclusion from the section summaries, not from re-reading all evidence.

This is the map-reduce pattern: multiple focused prompts beat one oversized prompt. It also makes citations tractable: each section knows which evidence ids it used.

5.7 Phase 5 — verification and uncertainty

After drafting, split the report into atomic claims and check each claim against its cited evidence:

VerdictAction
supportedKeep the claim and citation.
contradictedKeep both sides if credible; add a “sources disagree” note; prefer the newer/higher-quality source only with an explicit rationale.
unsupportedRemove, soften, or move to “speculation/commentary.” Never present it as fact.
backgroundKeep only if it is clearly marked as context and not attributed to a source.

The final report should include a short “What the sources do not establish” section. For the Jensen Huang question, that section is the most important part of the answer: the corpus establishes two publicly reported relationships, but not a verified total number of affairs.

.chat/research/<YYYYmmdd-HHMMSS>-<slug>/
  plan.json        # question, intent, subquestions, budgets

Append-only evidence is important: a crash or context overflow should not lose research progress. It also lets the UI show a “research trace” later.

5.9 Prompt contracts

Every structured call needs a strict schema and a repair path. The repo already has JSON helpers (_lfm_request_json, _lfm_request_json_stream, _lfm_parse_json_object) that can be reused.

Planner contract (small model):

Return JSON only:
{
  "intent": "fact | timeline | comparison | enumeration | causal | open_ended | speculation",
  "subquestions": [
    {"id":"q1","text":"...","type":"...","priority":1,
     "source_types":["corpus"],"seed_queries":["..."]}
  ],
  "stop_rules": {"max_rounds":3,"max_evidence_tokens":6000,"max_unique_sources":30}
}
Rules:
- 3 to 8 subquestions.
- For speculation/private facts, include separate questions for
  "reported", "confirmed", "speculated", and "unknown".
- Do not answer the question in the plan.

Gap-check contract (small model):

Return JSON only:
{
  "subquestions": [
    {"id":"q1","status":"answered | partial | unanswered",
     "missing":"specific missing facts or empty",
     "new_queries":["..."]}
  ],
  "contradictions": [
    {"claim":"...","sources":["E07","E12"],"resolution_needed":true}
  ],
  "stop": false
}
Rules:
- A subquestion is "answered" only if the evidence states the fact,
  not merely mentions the topic.
- New queries must target the missing fact, not repeat earlier queries.

Writer contract (35B):

Write the section "..." using ONLY the evidence below.
- Cite every factual sentence with [E##].
- Do not cite an evidence id that is not in the list.
- If the evidence does not support a sentence, omit the sentence.
- If sources disagree, say so explicitly and cite both.
- End with a one-line confidence note if the evidence is partial.
- Do not mention "chunk", "context", "provided documents", or internal ids.

6. Worked example: the Jensen Huang affairs question

The example in the prompt is deliberately hard: “how many affairs jensen huang might actually have?” It is partly a factual question, partly a rumor question, and partly unanswerable from public evidence. A single-shot RAG answer is likely to either invent a number, repeat commentary as fact, or refuse. A research-mode answer can do better.

6.1 What the corpus actually contains

The global corpus contains substantial reporting on the alleged affair scandal. Representative evidence found by the measured retrieval:

  • Alice Huang: multiple sources report an extramarital affair and say Huang admitted infidelity in a November 8 message to employees (Reuters, AP, CNBC and others). One source describes Alice Huang as a Chinese national and Megaspeed executive; another says the two are not related.
  • Kimberly Powell: The New York Times reported a second extramarital relationship with Nvidia’s vice president of healthcare, citing five people who had worked at Nvidia. One source notes that the second claim “remains unproven” and that neither Huang nor Powell acknowledged it.
  • “Two affairs”: several outlets describe “two extramarital affairs” or “reports of two extramarital affairs.” This is a report count, not a verified lifetime count.
  • Speculation: commentary in the corpus says things like “there would be at least two to five more women” and “I don't think we've seen the last woman.” That is opinion/commentary, not evidence of a number.

6.2 What a single-shot depth-100 answer tends to do

At depth 12–200 this question returned only 10 chunks, so depth did not add evidence. The risk is not “too little context”; it is epistemic: the model may merge admitted, reported, and speculated claims into one confident number. A larger context would not fix that. In fact, the depth-100 wagyu experiment shows that a larger context can make the model lose the instructions and the best evidence.

6.3 A research-mode plan

q1. Which relationships/affairs have been publicly reported by credible outlets?
q2. Which claims are confirmed or admitted, and which are alleged/unproven?
q3. Is there a verified count, and what do the company, court, or official
    statements say?
q4. Which claims are speculation or commentary rather than evidence?
q5. What remains unknown or unverifiable from the available sources?

6.4 What the final report should say

Answer: Public reporting names two relationships: Alice Huang (an extramarital affair that Jensen Huang admitted) and Kimberly Powell (a second relationship reported by The New York Times, which remains unproven and was not acknowledged by either person). There is no verified total number of affairs. Claims of “two to five more” women are commentary and speculation, not evidence. The defensible statement is: “At least two have been publicly reported; only one has been admitted; the actual number is unknown.”

This answer is more useful than a fake exact number, and it is faithful to the sources. It also demonstrates the research-mode contract: separate reported, confirmed, alleged, speculated, and unknown.

6.5 Why this beats “depth 100”

  • Depth 100 would not retrieve more than the 10 entity-focused chunks.
  • If it did retrieve more, it would risk crossing the 8k window and dropping the instructions and top evidence.
  • The research loop explicitly asks the questions that make the answer honest: what is confirmed, what is alleged, what is speculation, and what is unknown.
  • The evidence ledger makes each sentence traceable to a source and a date.

7.3 A/B protocol

Compare three configurations on the same suite:

  1. A: single-shot depth 12 (current default).
  2. B: single-shot depth 50 or 100.
  3. C: proposed research loop.

Use a single LLM judge with a rubric (factual accuracy, citation accuracy, completeness, source quality, uncertainty calibration), plus human review of the unanswerable/private question. 8. Rollout plan and immediate fixes

8.1 Phase 0 — make the current pipeline context-safe (hours)

  1. Add a prompt-budget check before stream_answer(): estimate_tokens(prompt) ≤ ANSWER_NUM_CTX − output_reserve. If it fails, drop the lowest-ranked context chunks until it fits and log the drop. Never let the runtime silently truncate the front.
  2. Reduce YOUTUBE_ITERATIVE_EVIDENCE_TOKENS and ARTICLE_ITERATIVE_EVIDENCE_TOKENS from 16,000 to a window-safe value (~6,000), or raise num_ctx and re-benchmark memory/TTFT.
  3. Show a warning in the UI when estimated context exceeds ~80% of the window.
  4. Keep DEFAULT_DEPTH = 12; use 25–50 only for list/long-form questions.
  5. Add a regression test for the wagyu depth-100 case: the answer must not exceed the context budget and must not cite chunk ids.

8.2 Phase 1 — minimal /research (days)

  1. Add /research <question> to WEB_COMMANDS and COMMAND_ARGUMENTS; stream phase logs and the final report.
  2. Implement the planner (3–6 sub-questions), per-sub-question retrieval, and an append-only evidence ledger.
  3. Reuse the existing iterative sufficiency check for 2 rounds.
  4. Write the report section by section from the ledger; cite evidence ids.
  5. Persist plan.json, evidence.jsonl, report.md, and trace.json under .chat/research/.

8.3 Phase 2 — verification and contradictions (1–2 weeks)

  1. Atomic claim extraction and claim-level support/contradiction checks.
  2. “Sources disagree” and “What the sources do not establish” sections.
  3. Source-quality labels (primary record / major outlet / aggregator / commentary).
  4. Newest-first ordering only when the question is time-sensitive; otherwise relevance first.

8.4 Phase 3 — source adapters and UI (later)

  1. Optional adapters for /news + news_fetch.php, Wikipedia, and official language docs when the local corpus is insufficient.
  2. “Open trace” panel with plan, rounds, evidence, and verification.
  3. Resumable research sessions and a “continue research” command.
  4. Evaluation dashboard using the metrics in §7.

9. Risks and guardrails

RiskMitigation
Hallucinated facts in the reportCitation contract, claim verification, unsupported-claim removal, “unknowns” section.
Treating rumors/commentary as factSource-quality labels; separate reported/confirmed/alleged/speculated; never infer a private fact from commentary.
Context overflow / silent truncationHard per-call token budget; trim lowest-ranked chunks; section-wise synthesis; log violations.
Over-decomposition and cost blow-upCap sub-questions and rounds; stop when marginal new evidence is low; simple questions get a simple plan.
Duplicate evidenceDeduplicate by chunk key, text similarity, and source cap; track “already used” evidence ids.
Stale evidenceUse published dates; newest-first for time-sensitive questions; explicitly date every claim.
Source bias / SEO content farmsPrefer primary records and major outlets; label aggregators and commentary; require independent corroboration for key claims.
Privacy / sensitive personal questionsReport only what credible sources say; avoid speculation; state the limits; do not turn rumor into a count.

A.3 Truncation reproduction sketch

import requests, chat

model = "ornith-1.5:35b"
filler = ("The quick brown fox jumps over the lazy dog. "
          "This paragraph is harmless filler used to measure prompt "
          "processing. It contains no question and no answer.\n")
head = "IMPORTANT: The secret access code is BANANA-42. You must remember it.\n"
tail = "\nQuestion: What is the secret access code? Reply with the code only.\n"
reps = max(0, ((12000 - chat.estimate_tokens(head + tail)) * 4) // len(filler))
prompt = head + filler * reps + tail

response = requests.post(
    "http://127.0.0.1:11434/api/generate",
    json={
        "model": model,
        "prompt": prompt,
        "stream": False,
        "think": False,
        "options": {"temperature": 0, "num_ctx": 8192, "num_predict": 12},
    },
    timeout=(10, 900),
)
data = response.json()
print("estimated:", chat.estimate_tokens(prompt))
print("evaluated:", data.get("prompt_eval_count"))
print("answer:", data.get("response"))
# Observed: estimated ~11,969; evaluated 4,098; the model did not know the code.
