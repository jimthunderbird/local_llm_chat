Why the first question is slow — and why continuous questions feel fast

Research for app/chat.html + app/chat_server.py · 2026-11-11 · macOS, 36 GiB unified memory, Ollama 0.40.14 · research only

TL;DR

The dominant cost is model load, not retrieval. The app tells Ollama to keep each model for 30m after the last request. Every question resets that timer. If you stop asking for longer than the timer — or if Ollama evicts a model to make room — the next question must load the 21.4 GB answer model again. Measured on this machine today, loading ornith:35b took a median of 5.9 s (up to 9.9 s), and the small qwen3:1.7b took 1.3 s. That time is paid before retrieval and before the first token.

Once you keep asking, the model stays resident, the OS page cache and prompt/KV cache stay warm, and the Python-side retrieval caches stay populated, so questions feel normal. A second, independent cause makes the problem look intermittent: the code calls the same answer model with different context sizes (32768, 16384, 8192), and Ollama reloads a model when the requested context length changes. So the first question after /wiki, 中文 translation, a line explanation, or an image question can be slow even inside the 30-minute window.

1. The observed symptom

Reported behaviour:

  • The first question of a session is slow.
  • If no question has been asked for a while, the next question is slow.
  • If questions are asked back-to-back, the speed is acceptable.

That is the classic shape of a cold model / cold cache penalty. The work that is repeated on every question — BM25 retrieval, prompt construction, and generation — is not the part that changes. The part that changes is whether the large model and its runtime state are still resident.

3.6 The first question of a server also warms process-level caches

The server does a good job at startup: it prewarms Ollama (chat.py:5196), loads the corpus, and builds/optimizes the global FTS5 index before serving (app/chat_server.py:13697–13730). But a few one-time costs still land on the first question:

  • _iterative_paragraph_chunks() builds a stable paragraph-only list for the iterative retrieval path and caches it in _PARAGRAPH_CHUNKS_CACHE (app/chat_server.py:6174).
  • get_bm25_index() caches by list identity (chat.py:1103, chat.py:1257). The filtered list is a different identity from the startup list, so its first use syncs and loads the index metadata again.
  • The expansion/filter cache (_EXPANSION_FILTER_CACHE, chat.py:2181), the 32-entry answer cache (AnswerCache, chat.py:937), and the acronym cache are empty.

These costs are small compared with a 21 GB model load, but they explain why the very first question after a fresh server start is slower than the second one even when the model is already warm.

4. Root causes, ranked

Cause 1 — keep_alive expiry reloads the 21.4 GB answer model primary

OLLAMA_KEEP_ALIVE = "30m" means each model stays loaded for 30 minutes after the last request that used it. Asking a question resets the timer, so a continuous session keeps the model resident. After more than 30 minutes of inactivity, Ollama unloads it. The next question pays the full cold load before retrieval and prefill. Today's median ornith load was 5.9 s; the all-time maximum was 15.9 s.

Why it matches the symptom: the delay appears only on the first question after a gap, and disappears when questions are frequent. That is exactly what a per-model idle timer produces.

Cause 2 — Ollama evicts models when memory is tight primary on this machine

With 21.4 GB for ornith, 1.9 GB for qwen, and ~3 GB for ministral, the working set is around 26 GB against a 28.1 GiB Metal budget and a 36 GiB machine that is also running macOS, Chrome, and a Docker VM. The scheduler logs predicted to exceed available memory, evicting and system_limited=true. A model can therefore disappear sooner than the 30-minute timer suggests, especially when a helper call asks for a different model or context size.

Why it matches the symptom: it explains why the first question is sometimes slow even when the user thinks the gap was shorter than 30 minutes, and why memory pressure (other apps open) changes the behaviour.

Cause 3 — context-size switching forces reloads intermittent

Ollama reloads a model when the requested num_ctx changes. The answer path uses 32768; translation uses 8192; line explanation and image questions use 16384; the wiki helpers use 8192. After any of those features, the next ordinary question reloads ornith at 32768. The log's -c distribution confirms that this happens in practice (17 loads at 8192, 25 at 4096, 9 at 16384 for ornith).

Why it matches the symptom: it makes the “first question after a while” look unpredictable, because the trigger is not only wall-clock idle time but also what the previous feature did.

Cause 4 — macOS memory pressure and swap secondary

The machine currently has 13% free memory and 11.16 GiB of swap in use. Even a “resident” model can have pages compressed or swapped out. The first post-idle request faults those pages back in; the second request finds them hot. This adds latency on top of the formal load timer and is worse when Chrome/Docker are busy.

Cause 5 — first-question cache warmup small but real

The first question after server start (or after switching scope) builds the paragraph-only BM25 view and populates the expansion/filter/answer caches. Startup prewarming covers the answer model and the small model but not every cache used by the iterative path. This is a one-time cost in the hundreds of milliseconds to a couple of seconds, not the main 6–16 s penalty.

5. Why continuous questions are fast

  • The keep-alive timer is refreshed on every request. A question every few minutes keeps ornith and qwen loaded; ollama ps shows the expiry moving forward.
  • Weights stay hot in the OS page cache and Metal residency set. No disk read, no GPU upload, no runner startup.
  • Prompt/KV cache can be reused. The prompt template and the leading part of the context are stable; Ollama reports cached prompt tokens in the benchmark line (prompt_tokens ... (cached ...)). A new context or a different model still pays prefill, but not the load.
  • Retrieval caches are already populated: _BM25_CACHE (by list identity), the paragraph list cache, the 512-entry expansion/filter cache, the 32-entry answer cache, and the acronym cache. Repeated questions and repeated evidence avoid duplicate small-model calls and index work.

Even warm, a question is not free: the log shows 2.7–5.6 s of prompt prefill for 1.6k–3.4k prompt tokens, plus retrieval (~0.5–2 s), plus generation at ~43 tokens/s. “Fast” here means “no 6–16 s model load and no cold cache”, not “instant”.

7. Recommendations

These are research recommendations; no code was changed for this task.

7.1 Highest leverage: keep the models resident

Add a lightweight keepalive watchdog to the server. Every 5–10 minutes, send a one-token (or empty) request with the same num_ctx the real calls use, for each model in the answer path — ornith (32768), qwen (8192), and ministral (8192). This refreshes the 30-minute timer without generating a real answer.

# pseudo-code, not implemented
targets = [("ornith:35b", 32768), ("qwen3:1.7b", 8192), ("ministral-3:3b", 8192)]
while True:
    sleep(5 * 60)
    for model, num_ctx in targets:
        POST /api/generate {
            "model": model, "prompt": "", "stream": false,
            "keep_alive": "30m",
            "options": {"num_predict": 1, "num_ctx": num_ctx}
        }

Expected effect: removes the 1.3–16 s cold load from the first question after a long gap. The first question then approaches warm latency. Tradeoff: the 21.4 GB answer model stays in memory (and in the Metal residency set) even when idle. On this 36 GiB machine that can increase memory pressure, so combine with the memory tuning below.

Alternative: set OLLAMA_KEEP_ALIVE=-1 (never unload) for the answer model. This is simpler but has the same memory tradeoff and can make the whole machine less responsive.

7.2 Use one num_ctx per model

Make every call to ornith:35b use the same context length (for example 32768), and every call to qwen3:1.7b/ministral-3:3b use 8192. In particular, change:

  • ANSWER_TRANSLATION_NUM_CTX (8192) to the answer context;
  • LINE_EXPLAIN_NUM_CTX (16384) and IMAGE_NUM_CTX (16384) to the answer context;
  • the generate_text() calls used by /wiki to pass num_ctx=ANSWER_NUM_CTX.

Expected effect: removes reloads after 中文 translation, line explanation, image questions, and wiki questions. Tradeoff: a larger context allocates a larger KV cache; if memory is the limiting factor, choose a single smaller context (for example 16384) and use it everywhere instead.

7.3 Prewarm the full answer path at startup

  • Add CONVERSATION_MODEL (ministral, 8192) to prewarm() targets; it is currently not prewarmed, so the first follow-up can pay a ~2–3 s load.
  • Prewarm the filtered paragraph list used by _iterative_paragraph_chunks() and call get_bm25_index() on it, so the first question does not build its metadata.
  • Keep the existing behavior of waiting for prewarm before serving; the current 120 s cap is reasonable, but log a warning if it expires so the first question is not silently cold.

7.4 Reduce memory pressure / evictions

  • Use ollama ps to see what is resident. Stop unused large models with ollama stop <model>.
  • Avoid keeping other 20 GB+ models loaded. The scheduler logs predicted to exceed available memory, evicting; each eviction becomes a future cold load.
  • If 36 GiB is consistently tight, consider a smaller answer model or a lower quantization, or close memory-heavy apps (Docker VM, many Chrome tabs) during long chat sessions.
  • Do not set OLLAMA_MAX_LOADED_MODELS=1 unless you accept model thrashing; keeping the answer model plus one small model is the useful minimum.

7.5 Hide the unavoidable cold start

If keeping a 21 GB model resident is not acceptable, warm it on user intent: when the browser input gains focus after an idle period, send a no-op warm request and show a small “warming model…” indicator. The user can start typing while the model loads, and the first real question is less likely to pay the full penalty. This does not remove the cost; it moves it off the critical path.

8. How to verify

  1. Use the built-in benchmark. In the chat, run /benchmark on and ask a question after an idle period. The benchmark line reports load, prefill, TTFT, and prompt_tokens ... (cached ...). A cold question has load > 0.5 s; a warm one has load < 0.05 s.
  2. Check residency. ollama ps shows model size, processor, context, and UNTIL. If the answer model is absent, the next question will be cold.
  3. Read the runner log. 
    grep -aE 'loading model via llama-server|predicted to exceed available memory' \
  ~/.ollama/logs/server.log | tail -40
  4. Check memory pressure. memory_pressure and sysctl vm.swapusage show whether macOS is paging the model out.
  5. Acceptance target. After the keepalive/unified-context changes, a question following 10 minutes of idle should report load < 0.05 s, and its TTFT should be within roughly 1 s of a back-to-back warm question.

11. Replacing ornith:35b with qwen3:1.7b

Added 2026-11-11. Research only; no application code was changed for this task. This section answers: is it feasible to use only qwen3:1.7b and remove ornith:35b, what breaks, and what configuration would be required?

Verdict: not feasible as a wholesale replacement. qwen3:1.7b is fast, small, and adequate for narrow helper tasks (query expansion, relevance filtering, translation, dictionary lookups, a simple /ask path). It is not a safe replacement for the final RAG answer, code generation, the math tutor, image questions, or long-context synthesis. The practical configuration is a hybrid: keep ornith:35b for the high-stakes answer path and use qwen3:1.7b where a small model is enough.

Option A — recommended hybrid (keep both)

Keep ornith:35b as the answer model and move only narrow helper roles to qwen3:1.7b:

# Follow-up resolver: prefer ornith; use qwen only with a rewrite validator

Use one num_ctx per model and prewarm both at those exact values (see §7.1–7.3). With qwen3:1.7b at 8192 the combined resident set is roughly 21 GB + 2 GB, which is much safer than 21 GB + 4.9 GB. If the machine is still swapping, lower the answer model's num_ctx to 16384 and retrieve fewer trunks rather than keeping a 32k KV cache resident.

Option B — full replacement (not recommended)

If the larger model must be removed anyway, use this configuration and accept a visible quality drop:

  • Model: qwen3:1.7b, non-thinking mode ("think": false); do not enable thinking for normal chat, because it adds latency and the app's prompts are not written for a reasoning trace.
  • Context: one value everywhere, preferably 16384 (32768 also works but doubles KV memory and prefill time). Native Qwen3-1.7B context is 32,768 tokens; do not exceed it without YaRN.
  • Sampling: Qwen3's non-thinking recommendation is temperature 0.7, top_p 0.8, top_k 20, min_p 0. For RAG/JSON extraction use a lower temperature (0.1–0.3); if repetition appears, add presence_penalty up to 1.5.
  • Output budget: cap normal answers at roughly 1024–2048 tokens. A 1.7B model does not benefit from a 32k output budget and long outputs are more likely to drift.
  • Retrieval: reduce depth from 25 to about 8–12 trunks. The smaller model is more easily distracted by tangential passages; the measured long-context test still retrieved a needle, but answer quality in the short RAG test was worse.
  • Guards: validate JSON, require citations, reject answers without a context citation, and fall back to a larger model for code, math, image, and low-confidence answers. Without these guards the failure is silent: the answer looks fluent but omits the relevant passage.
  • Keepalive: the existing 30-minute keepalive is fine; a 1.3 s cold load is cheap compared with 6 s for the large model.

12. If we commit to qwen3:1.7b only: configuration and prompt-engineering playbook

Added 2026-11-11. Research only; no application code was changed for this task. This is the follow-up to §11: assume the constraint is fixed — only qwen3:1.7b may be used — and design the best possible configuration and prompt engineering around that constraint.

Bottom line. A model swap alone will make this application worse. A 1.7B model can be made surprisingly competitive for narrow, schema-shaped jobs (query expansion, relevance selection, translation, dictionary lookup, a quick /ask) by giving it one job per call, a short context, an explicit output shape, and a validator. 12.3 Ten prompt-engineering rules that actually move a 1.7B model

  1. One job per call. Do not combine “decide if this is a follow-up”, “rewrite it”, and “classify the topic” in one prompt. Split them; each call is cheap at 85–106 tok/s.
  2. Put the instruction last, the immutable prefix first. Static role text and schema come first (so Ollama can reuse the prompt cache), the variable context next, and the actual task in the final lines. Small models overweight the most recent instruction.
  3. Show the output shape; do not describe it. A two-line example is more reliable than a paragraph of formatting rules. For JSON, pass a schema in format and still show one example.
  4. Use positive checklists, not prohibitions. “Write 3 bullets, one fact each” works better than “do not write long paragraphs”. Keep the list to three items.
  5. Quote first, answer second. Require the model to copy the exact supporting sentence (or its [S#] id) before writing the answer. This is the single largest groundedness improvement available without a bigger model.
  6. Use short IDs and require citations. Label passages [S1]…[S8], require [S#] after each claim, then verify the cited span with a string/token overlap check.
  7. Decompose lists and comparisons. “List every level of wagyu” is six smaller questions to a 1.7B model. Split the query, answer each part against its own retrieved evidence, then merge deterministically.
  8. Validate, then repair once. Parse the output; if it fails, send the exact error and the schema back with “return only valid JSON”. A second attempt fixes most format errors; a third is rarely worth it.
  9. Keep the working set small. Target 4–6k tokens of evidence, not 16k. The measured long-context needle test passed, but short-RAG answer quality was worse; a 1.7B model is more easily distracted by tangential passages.
  10. Calibrate refusal. Replace “if the context is insufficient, say so” with “answer the part the context supports, then list what is missing in one sentence”. The current small-model failure mode is over-refusal, not only hallucination.

12.4 Role-by-role prompt rewrites

12.4.1 Final RAG answer: extract, then write

The current answer template asks for grounding, no citations, conflict handling, aggregation, and refusal in one prompt. A 1.7B model will follow roughly half of that. Replace it with a two-pass pipeline:

# Pass 1 — extraction (JSON schema, temperature 0.0, num_predict 256)
System: You extract evidence for a question. Return only JSON.
User:
Question: {question}

Passages:
[S1] {passage_1}
[S2] {passage_2}
...
[S8] {passage_8}

Select at most 6 passages that directly help answer the question.
For each, copy the shortest supporting sentence exactly.
If no passage helps, return {{"evidence": []}}.

Schema:
{{"type":"object","properties":{{
  "evidence":{{"type":"array","maxItems":6,"items":{{
    "type":"object","properties":{{
      "id":{{"type":"string"}},
      "quote":{{"type":"string"}}
    }},"required":["id","quote"]}}
  }}
}},"required":["evidence"]}}
# Pass 2 — answer (temperature 0.3, num_predict 700, think=false)
System: You answer from the evidence below. Use only that evidence.
User:
Evidence:
{for each selected passage}
[{id}] {quote}
{end}

Question: {question}

Write:
1. A direct answer in 1–2 sentences.
2. Supporting details as 2–5 bullets. End every bullet with its [id].
3. If the evidence covers only part of the question, add one final line:
   "Not covered by the evidence: ...".

Rules:
- Use the same language as the question.
- Do not mention "passages", "chunks", or "the context".
- Do not add facts that are not in the evidence.

Why this works for 1.7B: pass 1 is a copy/classification task (its strongest mode), pass 2 sees only 3–6 short quotes instead of 20 mixed paragraphs, and the citation requirement gives a deterministic verifier something to check. If pass 1 returns no evidence, skip generation and return a calibrated “not found” message instead of letting the model improvise.

12.4.2 Query expansion: schema, five terms, no prose

The current prompt is already close. Make the output machine-checkable and cap it hard:

System: You write BM25 search terms. Return JSON only.
User:
Question: {question}

Return up to 6 terms that would appear in a document that answers the question:
synonyms, the full name of an acronym, and alternate spellings. Do not add
places, people, or facts that are not implied by the question.

Schema: {{"type":"object","properties":{{
  "terms":{{"type":"array","maxItems":6,"items":{{"type":"string"}}}}
}},"required":["terms"]}}

# options: temperature 0.1, num_predict 96, format = schema

Keep the existing corpus validation (a term must co-occur with a rare question anchor in at least 35% of its documents). A 1.7B model’s expansion is thinner but also less likely to invent an entity; the validation step matters more than the prompt.

12.4.3 Relevance filter / evidence sufficiency

This is a good small-model job, but only with a schema and a bounded candidate list:

Schema: {{"type":"object","properties":{{
  "keep":{{"type":"array","maxItems":12,"items":{{"type":"integer"}}}},
  "sufficient":{{"type":"boolean"}}
}},"required":["keep","sufficient"]}}

Prompt: Select the candidate numbers that contain information useful for
answering the question. Prefer recall: keep a candidate that covers part of
the question. Set sufficient=true only when the kept candidates contain every
fact the question asks for. Do not use outside knowledge.
Question: ...
Candidates: [1] ... [2] ...

Keep the existing rule that never discards the top lexical matches when the model returns an empty list. A 1.7B filter is most useful as a ranker, not as a veto.

12.4.4 Follow-up rewrite: few-shot plus a deterministic validator

§11 measured the failure directly: qwen returned “what time does it open on sunday” unchanged. A rule list alone does not fix that. Use two short examples and validate the result:

System: Rewrite the latest question as a standalone question, or return UNRELATED.
User:
Conversation:
Q: where is nijo market
A: Nijo Market is in Sapporo, near Odori Park.

Latest: when does it open
Standalone: When does Nijo Market open?

Conversation:
Q: where is nijo market
A: Nijo Market is in Sapporo, near Odori Park.

Latest: how do i cook pasta
Standalone: UNRELATED

Conversation:
{recent turns}

Latest: {question}
Standalone:

Then apply a validator before accepting the rewrite:

  • The answer must differ from the input (normalized case/punctuation).
  • It must contain a named entity or content word from the conversation.
  • It must end with a question mark for interrogative input.
  • If validation fails, fall back to the existing lexical relatedness heuristic and the original question. Never let a malformed rewrite replace a standalone question.

12.4.5 Translation (question and answer)

Qwen3’s multilingual training is a genuine strength, so translation is one of the safest roles. Two changes make it robust:

  • Translate one line or sentence group at a time, never a whole answer, and preserve list markers deterministically (the code already restores dropped prefixes).
  • Supply a small glossary block built from the conversation’s proper nouns (Nijo Market, Kyoto, Sapporo, ...) and say “keep these in Latin spelling”. This removes the main observable failure: translated place names.

12.4.6 Dictionary lookup

The four-field popup prompt is already schema-like. For 1.7B, make the shape non-negotiable and keep it under 80 words:

Word: {word}
IPA: {ipa or —}
Part of Speech: {pos or —}
Contextual Meaning: {one or two sentences, using the surrounding words}

Rules: exactly these four lines, one blank line between them; no quote section;
no title; if the word is unknown, say so in Contextual Meaning.

Validate that the reply contains the four labels; if not, retry once, then fall back to a plain “meaning / IPA / part of speech” template without the contextual sentence.

12.4.7 Code generation: retrieval, skeleton, then fill

This is the weakest role. Do not ask a 1.7B model to write “a complete CLI” in one shot. Use a staged prompt with the documentation excerpts already in context:

  1. Plan: “List the functions and the exact API names needed, one per line. Use only names that appear in the documentation excerpts.”
  2. Skeleton: generate signatures and types only, no bodies (num_predict 200).
  3. Fill: one function per call, with the relevant doc excerpt and the skeleton in the prompt.
  4. Check: run the language’s static checker (php -l, go vet, rustc --emit=metadata) and feed the first error back for one repair attempt.

Without a checker, at minimum reject code that references an identifier not present in the documentation excerpts or the skeleton. The existing per-language doc-search scripts (golang_doc_search.py, rust_doc_search.py, php_doc_search.py) are more valuable than any prompt trick here: they supply the correct API surface a small model cannot recall.

12.4.8 Math tutor: thinking for solving, schema for generation

  • Problem generation: keep think=false, temperature 0.1–0.2, batches of 3–5 (not 10), and a JSON schema with exactly topic/question/answer. A 1.7B model truncates long arrays; small batches plus the existing avoid-list are the fix.
  • Solving/grading: think=true is worth the tokens. Cap thinking with num_predict and require a final “Check by substitution” line. The verifier pass (“substitute the answer back into the original equation”) catches more arithmetic errors than a longer explanation.
  • Graphs: keep the existing JSON contract and validate it; a 1.7B model will occasionally emit malformed JSON, and the front end already falls back to a code block.

12.4.9 Simple /ask and the podcast

/ask is explicitly a quick-answer path; 1.7B is acceptable there. For the AI podcast, generate an outline first (5–8 HOST/GUEST beats as JSON), then expand one beat per call. A single prompt asking for 2,000 words will drift or repeat; per-beat generation keeps the two voices and the story arc stable.

12.6 Guardrails: the part that replaces model capability

  1. Schema-constrained JSON. Pass a schema in format for expansion, filtering, extraction, follow-up classification, math batches, and the podcast outline. Never parse free-form JSON with a regex alone.
  2. Citation verifier. For each [S#], require the cited passage to share a minimum token overlap with the claim (or contain a quoted span). Unsupported claims are dropped or marked.
  3. Entity/number check. Extract capitalized entities and numeric values from the answer and confirm each appears in the evidence; flag or remove unsupported ones. This catches the classic 1.7B failure of inventing a price or a date.
  4. Repair loop. One retry with the parser error and the schema. Stop after two attempts and return a deterministic fallback.
  5. Refusal policy. Distinguish “no evidence at all” (state not found) from “partial evidence” (answer the supported part, name the gap). The current all-or-nothing refusal is wrong for a small model.
  6. Evaluation set. Keep 30–50 real questions with known answers from the current corpus. Track: supported-answer rate, unsupported-claim rate, citation accuracy, refusal on answerable questions, JSON validity, and p50/p95 latency. Prompt changes must be measured against this set, not judged by one impressive answer.

12.9 Recommendation

If “only qwen3:1.7b” is a hard constraint, build the extract → verify → write pipeline before touching another prompt. That pipeline, plus schema-constrained JSON and a repair loop, is worth more than any wording change. Expect helper roles to match the current behaviour, expect simple factual RAG answers to remain usable, and expect code generation, multi-step math, and high-stakes synthesis to stay below ornith:35b. Keep the evaluation set and the calibrated “partial answer + gap” response so the remaining quality loss is visible instead of silent.

If the constraint can be relaxed later, the cheapest upgrade is not a 35B model for everything: it is a single larger answer/code/math model used only on the paths that fail the acceptance criteria, with qwen3:1.7b handling all helpers. That preserves most of the memory and speed benefit while keeping the risky paths reliable.

13.1 What the model actually is

The Ollama tag milodule3/LFM3-1.7B-aura-grounded:latest is a third-party fine-tune, not an official Liquid AI model. It is built on LiquidAI/LFM3-1.7B, a 1.73B text model with a 24-layer tri-hybrid architecture (13 gated short convolutions, 5 sliding-window-attention layers with a 256-token window, 6 global-attention layers), a 128k vocabulary, a 256K-token context window, and 16 supported languages. 13.6 How to integrate without breaking the current stack

The working tree currently uses ornith:35b for every text role. Three options, in order of preference:

  1. Verifier alongside ornith (recommended). Add a GROUNDING_MODEL constant and a small verification module. Use it only for: (a) pre-answer sufficiency on contexts above roughly 8k tokens or high-risk questions (prices, dates, visa/medical/legal rules), and (b) post-answer claim checks. Keep ornith:35b as the writer. Set OLLAMA_MAX_LOADED_MODELS=2 and refresh both models in the watchdog. Expected benefit: fewer confident wrong answers and no change to answer style.
  2. Retire qwen3:1.7b, keep one small model. Since qwen is already gone from the text roles, this is mostly a documentation change. Use LFM3 for verifier / relevance / refusal, and keep ornith for generation. This is the cheapest way to get the anti-hallucination benefit.
  3. Make LFM3 the primary answer model (not recommended). It requires adopting its [n] Title evidence format, removing the app's competing refusal instruction, capping answers at a few sentences, and accepting weaker synthesis, code, math, and translation. It would save memory (2.05 GB vs 21.4 GB) and prefill time, but the product would answer less, not better.
Do not put it behind the same num_ctx-changing code path. Ollama reloads a model whenever the requested context size changes, and the app currently uses 32,768 everywhere. Keep that single value for LFM too. If a verifier needs 64k or 128k, it will pay a reload; pass the same 32,768 unless the job genuinely needs more.

13.8 Recommendation

Adopt LFM3-aura-grounded as a grounding/refusal verifier, not as the answer writer. It is the best model tested at the one thing this RAG stack most needs: declining when the evidence is insufficient, without inventing a price, a stall count, or a location. Its 32k footprint (2.05 GB) and prefill speed (1.2–1.5k tok/s) make it practical to run beside ornith:35b and to verify long evidence cheaply. Its weaknesses are exactly the roles that need free-form generation: long answers, follow-up rewriting, translation, code, and math. Do not replace qwen3:1.7b wholesale with it; replace only the verifier/relevance/refusal roles, keep deterministic validation and JSON schemas, and keep a larger writer for the final response.

If the goal is simply to retire qwen3:1.7b, this model is a defensible replacement for grounding and a regression for generation. If the goal is to make the existing ornith-based app more trustworthy, adding it as a second model is the highest-value use. If the goal is to make the app cheaper and faster overall, the memory and prefill savings are real, but decode is slower than qwen and the current ornith writer is still the quality ceiling.

14.1 Why the current answer path fails, and what can be overridden

The local manifest bakes in a system prompt that says “answer in one or two sentences” and “if the documents don't contain the answer, reply with exactly: I couldn't find the answer in the provided documents.” The application's research/100_trunks_prompt.txt adds a different refusal sentence and asks for a synthesis. The two contracts conflict. In the synthetic test suite, the unmodified path produced:

  • Answer then refusal: for “What time does Nijo Market open, what does it sell, and where is it?”, it answered correctly and then appended “The provided context does not contain sufficient information to answer this question.”
  • Reasoning leakage: for “List all the wagyu cuts mentioned”, it emitted “Wait, let me re-read the chunks…”, quoted chunk text, and then appended the refusal sentence, even though it had already listed all six cuts.
  • Blanket refusal: for the 250-word Nijo article it returned only the refusal sentence, because the baked “one or two sentences” contract was still active.

The good news is that Ollama's system request field replaces the baked system prompt. Passing a custom system prompt removed the one-or-two-sentence cap and the baked refusal sentence. The remaining problem is that a prompt-only fix is not enough: the DPO alignment still tends to append a refusal after a substantive answer, and it treats “the evidence does not contain a complete answer” as “the evidence is insufficient.” The pipeline below fixes both with structure, not with more prose.

14.2 Recommended architecture: a relevance gate, then a writer

Do not ask one call to decide relevance, completeness, refusal, length, style, and entity scope at once. Split the job into two JSON-schema calls:

  1. Gate call (cheap, deterministic). Ask only: “Does the evidence contain at least one fact that directly helps answer the question?” Return {"relevant": true|false}. Use temperature=0, num_predict=32, and no few-shot examples. This call is the refusal decision. If it returns false, return the application's refusal sentence without asking the writer to refuse.
  2. Writer call (grounded, complete). Ask the model to answer every part the evidence supports, in its own words, with no refusal instruction at all. Return {"answer": "..."}. Use temperature=0.1, num_predict=600–1200. Because the output is schema-constrained to one JSON object, the model cannot append a second refusal paragraph or an “Evidence:” section.

This split is the single most important trick in this section. The model is good at the narrow gate question, and it is good at writing once it has been told that the evidence is relevant. It is bad at doing both at once. The gate also gives us a clean place to implement “partial answer” behavior: a question about where to get an IDP is relevant=true because “obtain it before arriving in Japan” is a partial answer, while a question about the number of stalls is relevant=false because the evidence only names the market and never discusses stalls.

Question: What time does Nijo Market open, what does it sell, and where is it?

More important than the format is precision. The current app can feed the model up to 20 BM25 chunks and 4,096 estimated context tokens. LFM3-aura is much more distractible than ornith:35b. In a real-corpus test, a Nijo Market article retrieved two chunks whose bodies were about the adjacent Sapporo Morning Market (5am opening, blankets and folding chairs). The model transferred those facts into the Nijo article. A wagyu “levels” question retrieved a video chunk about “ten levels of Wagyu” and the model answered about the video instead of the grading taxonomy. These are retrieval-side failures that no prompt can fully repair.

For an LFM-primary stack, change retrieval in four ways:

  1. Prefer precision over depth. Use 8–12 chunks, not 20. On the wagyu test, the top 8 chunks still contained the grading facts; the distractor video entered at position 10. A smaller, cleaner context is better for a 1.7B writer. Keep the existing relevance filter if it is available, or run the LFM gate as a per-chunk filter with a JSON schema.
  2. Apply an entity-body filter. If the question names an entity (“Nijo Market”, “Terence Tao”, “wagyu”), drop chunks whose body does not mention that entity, even if the title does. This removes sibling-entity chunks that mention the target only in a title or intro. Do not drop the top lexical match; apply the filter only when it leaves enough evidence.
  3. Drop junk and duplicates. The real corpus contains nav text, photo captions, “Delicious Beautiful Spectacular JAPAN”, “#Foreign Tourists#Hokkaido#Tourism”, “### CARTOON OF THE DAY”, and duplicate bodies with different ids. Deduplicate by normalized paragraph text and require at least a handful of content words. This alone removed several distractors from the Nijo context.
  4. Add intent terms for list/taxonomy questions. For “levels of wagyu”, include grading vocabulary in the BM25 expansion: grade, A1, A2, A3, A4, A5, BMS, yield, quality, marbling. This pushes the grading chunks above the “ten levels of Wagyu” cooking video.

14.8 Quality boundaries and escalation policy

Use LFM as the primary writer for: short factual questions, single-entity questions, explicit lists, yes/no rule questions with direct evidence, partial answers, conflict detection, and Simplified Chinese questions with the explicit language block.

Do not expect ornith-level quality for: 200+ word features, multi-entity comparisons, dense taxonomies (wagyu grades, visa categories), code generation, math, or translation of nuanced prose. On those tasks the measured gap is large, not marginal.

If the product can keep a second model on disk but not resident, use an escalation policy: LFM handles the default path; route to ornith:35b (load on demand) when the question matches a long-form/code/math/translation intent, when the gate is true but the writer answer is shorter than the requested length, or when the answer mentions a sibling entity that the question did not ask about. If only LFM may run, accept shorter answers and invest in the retrieval filters in §14.4. Do not promise 35B-quality long-form from a 1.7B writer; the measurements do not support it.

def clean_answer(text):
    text = re.sub(r"\[\d+(?:,\s*\d+)*\]", "", text)
    text = re.sub(r"\b(?:chunk|source|note|document)\s*\d+\b", "", text,
                  flags=re.I)
    text = re.sub(r"^(?:The provided context|The evidence|The documents)\s+"
                  r"(?:states?|says?|shows?)\s+(?:that\s+)?", "", text, flags=re.I)
    text = re.sub(r"\bthe provided context\b", "", text, flags=re.I)
    text = re.sub(r"\s{2,}", " ", text).strip()
    return text

Post-processing is intentionally small. The gate decides refusal; the writer should not be asked to produce a refusal sentence, and the JSON schema prevents most of the old leakage. The cleaner is only a safety net for [1], “the provided context”, and stray whitespace.
