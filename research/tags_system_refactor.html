Soft Tags: Replacing Physical Tag Files with a tags.json Context Registry

Research report for prompts/tags.prompt · 2026-11-05 · Scope: app/chat.html, app/chat_server.py, and the chat.py retrieval library · research only no application code was changed

Read this first. The tag system should become a soft, query-time context backed by one registry file (tags.json), not a set of physical membership files under ./tags. Retrieval should start from the question over one global trunk corpus, then apply the tag context as a second, soft relevance signal. Video ingestion should not run a 35B classification call per tag. The recommended design keeps the existing BM25, query expansion, small-model filter, streaming, and prompt pipeline; it changes where tag metadata comes from and how tag relevance is computed.

1. Executive summary

The current tag feature is a hard partition. ./tags/<tag> contains YouTube video ids; chat.load_chunks(tag) loads only those videos; /tag rebuilds the in-memory trunk list; the cross-tag fallback loads the union of every tag file and tries other tags one at a time. Learning a video ends with youtube_video_tag_gen.py, which asks ornith:35b one yes/no question for every tag. On this machine one such classification took 11.8 s for a single video/tag pair. With the current 13 tags that is roughly 2.5 minutes of tagging added to every new video, and a full reclassification would be thousands of 35B calls.

The repository already has 497 learned videos and 10,660 trunk files. A single global BM25 index over all of them is practical: measured index build time was 1.34 s and the index used about 61 MB of Python memory (tracemalloc), on top of the process. That makes the hard tag partition unnecessary as a memory-saving device.

Recommendation. Make tags.json the only tag registry. Each tag has a description (and optionally a small keyword list). Learning stops at transcript, rewrite, trunks, and embeddings. At query time:

  1. Retrieve question candidates from the global trunk corpus with the existing BM25/expansion/fuzzy-entity machinery.
  2. Apply a tag-aware relevance step over those candidates. Use the existing qwen3:1.7b filter with the tag description added to its prompt (measured 0.2–2.7 s), and keep a lexical tag-profile re-rank as the cheap fallback.
  3. Put the tag name and description into the answer prompt as scope instructions, never as evidence.
  4. If no candidate satisfies the tag context, route to the best other tag in one small-model call (or a lexical tag ranking), instead of running a 35B answer attempt for every tag.

This preserves the user-visible meaning of /tag (“answer within this topic”) while removing per-video tagging latency, duplicate membership data, and the stale hard partition.

3. Why the physical tag files hurt

3.1 Learning latency is dominated by classification

The tag classifier loads up to 2,500 characters of title/rewrite/transcript for each video and asks ornith:35b one yes/no question per tag. On this machine a single call took 11.8 s in a controlled experiment. The current pipeline therefore adds roughly:

ScenarioCallsApprox. time at 11.8 s/call
One new video, 13 tags13~2.5 minutes
Full re-tag of 497 videos, 13 tags6,461~21 hours (gross)
Full re-tag minus 1,137 recorded positives5,324~17.5 hours (sequential)

These are order-of-magnitude numbers, not a benchmark of every machine. They show why removing per-video tagging matters: the cost scales with videos × tags, and every new tag multiplies the backfill.

3.2 The hard partition is duplicated, stale, and lossy

  • Duplication: 1,137 membership lines for 470 unique videos. A video about AI coding can be stored in four or five files.
  • Staleness: a tag file records a yes/no decision made from a 2,500-character excerpt. Re-learning a video does not automatically remove old memberships or add new ones beyond the classifier pass.
  • Lossy boundaries: tag membership is binary. A video that touches Japan for one segment but is mostly about AI cannot be partially relevant; it is either in or out.
  • Invisible untagged videos: 27 learned videos are not in any tag. Under hard tags, they can never answer a query; under soft tags they are natural candidates.

3.3 Cross-tag fallback is expensive and indirect

The current fallback first builds/loads the union of every tagged video, ranks tags by BM25 evidence, then calls the 35B answer model once per attempted tag. With soft tags there is one global corpus and one candidate set; tag routing can be a single small-model decision. This removes both the union-index rebuild and the repeated 35B attempts.

4. Requirements and meaning of “soft tag”

“Soft” should mean: the tag is resolved at query time from metadata, not from a precomputed list of video files. It should not mean “the tag is only a cosmetic label.” The intended behaviour is a conjunction of two relevance conditions:

Scope condition. A context trunk qualifies only when it is relevant to both the active tag context (name + description) and the user's question. The tag condition is evaluated when the question is asked, not when the video is learned.

Concrete requirements derived from the prompt and the existing product:

IDRequirement
R1tags.json is the single source of truth for valid tags and descriptions.
R2A tag absent from tags.json is invalid: /tag, CLI --tag, and completion must reject it.
R3Learning a video must not depend on tags: fetch transcript, rewrite, create trunks, create embeddings, done.
R4/tag <name> sets a global tag context; it must not rebuild a hard video subset.
R5For a question, context selection combines tag-context relevance and question relevance.
R6The tag description participates in retrieval and/or answer construction; it is not merely displayed.
R7Out-of-tag questions should not silently use unrelated content without a visible explanation; preserve or improve the current auto-switch behaviour.
R8Existing coding/documentation tags (golang, rust, php) must keep working.

5. Design options

OptionHow the tag is appliedPros ConsVerdict
A. Prompt-only tag context Retrieval is global question BM25. The tag name/description is prepended to the answer prompt. Simplest; no new model calls; no false retrieval negatives. Does not satisfy “fetch trunks related to the tag”; a model may ignore the scope or answer from unrelated chunks. Insufficient alone
B. Description-weighted BM25 Add tag-description terms to the query, or score chunks by description BM25 and combine with question BM25. Cheap, deterministic, no extra model; easy to cache. Descriptions contain common words. Measured: 10,652 of 10,660 chunks had a positive BM25 score for the ai_and_coding description. Requires stopword removal, keywords, and calibration. Useful as a prior, not as a hard gate
C. Two-stage soft-AND filter Retrieve top question candidates globally, then ask a small model to keep only candidates that are both question-relevant and tag-relevant. Directly implements the requirement; measured 0.2–2.7 s; reuses the existing qwen3:1.7b filter infrastructure; no embeddings. Small model can be wrong; must define NONE/error behaviour; adds TTFT unless parallelised. Recommended primary
D. Lazy LLM tag classification per video Classify video/tag pairs on demand and cache the result in a derived index. Good accuracy; no per-chunk ambiguity. Reintroduces the expensive classifier, only later; cache invalidation and cold-start cost; violates the spirit of removing tag generation. Reject as default
E. Strict lexical prefilter Only videos above a tag-profile lexical threshold enter the candidate set. Fastest and most deterministic. Severe false negatives. Example: the Nijo Market video ranks 189/497 against the Japan profile because its rewrite mentions “Japan” only once; keyword expansion improves it to 42/497, but lexical matching alone is not reliable. Optional strict mode only

6. Recommended architecture

Use C as the primary tag gate, with B as a cheap prior/fallback and A as the prompt-context layer. Keep one global trunk corpus and one BM25 index. The tag is metadata on the query, not a partition of the corpus.

6.1 Registry: tags.json

Keep the existing description-map shape for the minimum migration: 

{
  "japan": "Japan, Japanese culture, society, economy, history, language, travel, and people or organizations from Japan.",
  "golang": "The Go programming language: syntax, concurrency with goroutines and channels, the standard library, tooling, performance, backend services, and Go ecosystem practices."
}

For better retrieval, allow a backward-compatible object form with optional keywords. A loader can accept both strings and objects and normalize them: 

{
  "japan": {
    "description": "Japan, Japanese culture, society, economy, history, language, travel, and people or organizations from Japan.",
    "keywords": ["Sapporo", "Hokkaido", "Tokyo", "Kyoto", "Osaka", "Fukuoka", "Okinawa", "ramen", "sushi", "wagyu"]
  }
}

Keywords are static tag metadata, not per-video classifications. They are the cheapest way to repair the lexical profile when a description uses generic words. In the experiment, adding a small Japan keyword list moved the Nijo Market video from rank 189/497 to rank 42/497 and the wagyu video from rank 51/497 to rank 41/497 against the video-level profile.

Validation rules for the registry:

  • File missing, invalid JSON, non-object root, empty object, or a non-string/non-object value: fail fast with a short, actionable error.
  • Detect duplicate keys (for example with json.load(..., object_pairs_hook=...)) instead of silently accepting the last one.
  • Tag names must be non-empty, must not contain /, \, . or .., and should follow the existing lowercase snake_case convention. Reject path-like names even though they are no longer filenames.
  • Descriptions must be non-empty after whitespace normalization.
  • Expose a stable tags_version (mtime + size, or a content hash) for answer-cache invalidation and hot reload.

6.2 Ingestion: remove tagging from the learning pipeline

youtube_video_learn.STEPS should become four steps: 

STEPS = [
    ("fetch_youtube_transcript.py", ["<hash>"]),
    ("rewrite.py", ["<hash>"]),
    ("create_trunks.py", ["<hash>"]),

]

Update the docstring, the help text, and the progress weights in app/chat_server.py (VIDEO_LEARN_STEP_WEIGHTS currently has five entries matching the five steps). Remove the youtube_video_tag_gen.py progress branch. Archive or delete youtube_video_tag_gen.py after the migration; leaving it runnable would encourage the old model. The completed prompt item that renamed generate_tags.py to youtube_video_tag_gen.py remains historically true, but this refactor supersedes its role.

6.3 Startup and /tag

  • Load tags.json once at startup and cache the normalized profiles. If the default tag is absent, fail with the valid tag list (do not silently create it).
  • Load the global chunk list once: load_chunks(video_ids=set(available_video_ids())). Add a dedicated load_all_chunks() wrapper so the loader prints “10,660 trunks from 497 videos” instead of a huge transcript-id list.
  • /tag <name> validates against the registry and changes only state.tag and state.tag_description. If the current scope is a transcript or an article, restore the global corpus first; otherwise no chunk reload and no BM25 rebuild are needed.
  • /tag should clear the answer cache because the prompt/scope changed. Whether it resets the conversation is a product decision (today it does; consider keeping conversation for a metadata-only switch).
  • Completion, CLI --tag (including the interactive “no value” form), and /status read the registry keys. The status payload should include the description or a short “soft tag” label so the UI can explain the scope.
  • Remove /tag_gen and /youtube tag_gen from the command tables and completion paths. If backwards compatibility is required for one release, make them print a deprecation notice and point to tags.json; do not keep writing tag files.

6.4 Retrieval: global question retrieval, then tag-aware soft-AND

  1. Question retrieval. Run the existing top_chunks() over the global chunk list. This already includes query expansion, fuzzy spelling correction, entity focus, score elbow, per-video caps, and the small-LLM question filter. It returns a question-relevant candidate set (default depth 20).
  2. Tag-aware filter. Add a separate function, tag_filter_candidates(question, candidates, profile), using the existing FILTER_MODEL (qwen3:1.7b). Its prompt contains the tag name, description, optional keywords, the question, and numbered 700-character candidate snippets. It must return the numbers that satisfy both conditions, or NONE.
  3. Do not reuse the question filter's safety nets. The current filter_candidates() deliberately keeps the top FILTER_ALWAYS_KEEP candidates and, when the model says NONE, keeps FILTER_FALSE_NEGATIVE_KEEP top BM25 candidates. Those are correct for question relevance but would defeat a strict tag gate. Give the tag filter its own return status: ok, none, skipped, error. Only ok candidates answer the question. On none, route to another tag or report the scope miss. On error, fall back to the lexical tag prior and log.
  4. Lexical prior / fallback. Build a tag profile from description + keywords and compute BM25 scores over the candidate chunks or over a small per-video profile index. Normalize the tag score within the candidate set and use it to (a) pre-rank tags for the router and (b) re-rank candidates when the small-model filter is unavailable. Keep the question score dominant: score = s_question * (1 + alpha * normalized_tag_score) with alpha around 0.25–0.5. A strict mode may additionally require tag_score > threshold.
  5. List questions. The current question filter is skipped for list/aggregation queries. Do not skip tag scoping there. Run the tag filter in batches of at most 20 candidates (or use the lexical prior) so “list all X in this tag” still gets broad, scoped context.
Why not rely on description BM25 alone? A direct BM25 query using the unmodified ai_and_coding description scored positively on 10,652 of 10,660 chunks; the japan description scored positively on 10,389. Removing stopwords reduced the positive counts to 3,813 and 3,152, but the scores still need per-tag normalization. A description is a topic summary, not a boolean classifier. Use it as a prior, or hand the decision to the small model that can read the candidate.

6.5 Tag context in the answer prompt

Add a compact scope block through the existing prompt_prefix mechanism. It must be clearly labelled as instructions, not as evidence, so the prompt's grounding rule still applies: 

<tag_context>
Tag: japan
Description: Japan, Japanese culture, society, economy, history, language, travel, and people or organizations from Japan.
</tag_context>
The user is currently exploring this tag. Prefer context that fits this topic.
Do not use this tag description as a source of facts, and do not answer from
outside the provided chunks. If the provided chunks are all outside this topic,
say so plainly.

Combine this with the existing coding_prompt_prefix(tag) when the tag is a documentation-backed language tag. Keep the tag block short: it is repeated on every answer and should not crowd out the retrieved context.

6.6 Cross-tag fallback without hard tag files

Replace fallback_tag_order() and the repeated 35B attempts with a tag router over the same candidate set:

  1. Run the tag-aware filter for the active profile. If it returns candidates, answer normally.
  2. If it returns NONE, rank the other registry tags. Cheap first pass: mean/median normalized lexical tag score over the top question candidates. If the best tag is clearly ahead, select it. Otherwise make one qwen3:1.7b routing call with the question, candidate snippets, and the tag names/descriptions, asking for the single best tag or NONE.
  3. Re-run the tag filter once with the selected profile. If it succeeds, update state.tag/description (keeping the conversation, as adopt_tag() does today) and stream the answer.
  4. If no tag fits, either answer with a clear scope message or, if product policy prefers the current always-answer behaviour, answer from the top question candidates and log that no tag matched. Do not silently pretend the active tag covered it.

This reduces fallback from “N answer-model attempts” to one router call plus one answer. It also eliminates load_all_tagged_chunks() and tags_containing_video().

6.7 Learning refresh

After a successful learn, invalidate the global knowledge signature and the answer cache. If the active scope is an article or a single transcript, leave it unchanged, as today. Otherwise, make the new video available without a restart: either append its chunks to the in-memory list or reload the global chunk list (chunk-list loading is cheap; the BM25 index is rebuilt lazily on the next question). Remove the video_is_tagged gate entirely.

6.8 Cache, status, and UI

  • Include tags_version (or the profile hash) in the answer cache key; editing a description must invalidate cached answers.
  • Hot-reload tags.json when its mtime/size changes. Clear the answer cache when the version changes; do not rebuild the BM25 index unless the retrieval implementation embeds tag metadata into it.
  • The status bar currently shows the tag and trunk/video counts. With a global corpus, label the scope honestly, for example “soft tag: japan · global 10,660 trunks / 497 videos”, and expose the description in /status or a tooltip.
  • Update help text, WEB_COMMANDS, YOUTUBE_SUBCOMMANDS, and the HTML completion logic that currently special-cases /tag and /tag_gen.

6.9 Proposed retrieval pseudocode

def answer_in_tag(question, state, registry):
    candidates = top_chunks(question, state.all_chunks, limit=state.depth)
    if not candidates:
        return no_evidence()

    profile = registry[state.tag]
    decision = tag_filter_candidates(question, candidates, profile)

    if decision.status == "ok" and decision.kept:
        return generate_answer(question, decision.kept, profile)

    if decision.status == "error":
        kept = lexical_tag_rerank(question, candidates, profile)
        return generate_answer(question, kept, profile)

    # status == "none" (or no kept candidates)
    routed = route_tag(question, candidates, registry, exclude=state.tag)
    if routed is not None:
        state.tag = routed
        profile = registry[routed]
        decision = tag_filter_candidates(question, candidates, profile)
        if decision.status == "ok" and decision.kept:
            return generate_answer(question, decision.kept, profile)

    return scope_miss(state.tag, routed)  # or explicit global fallback

9.2 Unit and integration checks

  • Registry: missing file, malformed JSON, duplicate keys, empty registry, invalid tag names, string and object forms, hot reload.
  • Commands: /tag valid/invalid/no-argument; CLI --tag valid/invalid/interactive; completion; status payload; /tag_gen deprecation or removal.
  • Retrieval: tag filter returns ok/none/error; list queries still get tag scoping; the top question candidates are always inspected before a tag miss is declared.
  • Learning: new video becomes available without a tag pass; article/transcript scopes are unchanged; progress weights sum to 100.
  • Cache: editing tags.json invalidates answers whose prompt used the old description; switching tags does not reuse the previous tag's answer.
  • Performance: global index build under 2 s on this corpus; subsequent retrieval under 200 ms; tag switch under 50 ms when already in global scope; memory well under the current process budget.

9.3 Quality metric

For each regression question, record the set of source video ids retrieved before and after the refactor. Report precision@k and recall@k of the expected videos, plus whether the tag filter changed the set. Do not evaluate only the final prose: the answer model can hide a retrieval regression by writing a plausible paragraph from the wrong sources.

11. Open decisions

  1. Strictness. Should a question outside the active tag auto-switch to another tag (today's behaviour), or return a scope message? Recommendation: auto-switch first; if no tag fits, explain the scope instead of silently answering from unrelated chunks.
  2. Registry schema. Keep a pure string map, or allow the object form with keywords? Recommendation: accept both; strings are the minimum migration, objects are the quality path.
  3. /tag conversation reset. Today /tag drops the conversation. A metadata-only tag switch could keep it. Recommendation: keep the current reset for predictability, or make it a small option.
  4. /tag_gen. Remove it, or repurpose it as a read-only validator/explainer for the registry? Recommendation: remove the classifier semantics and the command; keep a separate maintenance script if editing tags from the CLI is desired.
  5. Default tag. Keep japan as the default (it is embedded in prompts and tests) and require it in the registry.
  6. Embeddings. Do not reintroduce embeddings for tag affinity. The current architecture deliberately removed them; the small model filter and lexical profile are sufficient and cheaper.
