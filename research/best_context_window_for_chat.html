Best Context Window for the Local Chat

Research for task.research.best_context_window_for_chat in prompts/chat_common.prompt. Date: 2026-11-18. Scope: the current local setup (app/chat_server.py, chat.py, Ollama, ornith-1.5:35b).

Bottom line. Use a 32,768-token model context window for chat, while keeping the retrieved answer context at 8,192 tokens. The designed maximum working set for a turn is roughly 10–12k prompt tokens (8k of evidence plus instructions and output budget); default-depth turns are usually much smaller. So 32k is useful headroom, not a target to fill. On the 36 GB M3 Pro, a 32k window should cost about 22.3 GB resident (weights + KV cache), leaving roughly 6–7 GB for macOS and other applications. The current 16,384-token window already works; 32k is recommended because it gives room for long user questions and code without a meaningful quality or latency penalty. Do not raise chat to 64k or 128k: the memory benefit is small, the quality benefit is unproven, and the machine becomes memory-constrained. For long conversations, do not grow the window. Keep a rolling summary plus the last 4–6 turns, store durable facts in a small searchable memory, and retrieve only what the current question needs.

What the conversation actually contributes

The browser keeps the visible transcript, but the answer prompt does not receive the full transcript. On each question the server:

  1. Compares the question with the last up-to-8 turns.
  2. If it looks like a follow-up, a small model rewrites it into a standalone retrieval question (for example “when does it open?” becomes “When are the opening hours of Nijo Market?”).
  3. Runs BM25 retrieval for that standalone question.
  4. Writes the answer from the current retrieved evidence, not from the entire chat history.

This is an important design choice: conversation length does not make the answer prompt grow linearly. It also means the current 16k window is mostly spent on retrieval + instructions + output, not on chat history.

2. Three different “context” numbers

Most confusion about context windows comes from treating three separate limits as one. In this application they are:

LimitCurrent valueWhat it controlsShould it grow with conversation length?
Model context window (num_ctx) 16,384 Total tokens the model can see in one call: instructions, retrieved evidence, conversation material (if any), and generated answer. No. It should be sized to the largest single-turn working set, not to the number of turns.
Retrieved answer context 8,192 Estimated tokens of BM25 trunks selected as evidence. No. It is a relevance budget; more evidence eventually hurts precision.
Conversation memory 8 turns × 900 answer chars Material used to resolve pronouns and follow-ups; not inserted wholesale into the answer prompt. Only the summary/fact store should grow, and it should be compacted.
Answer output budget ~1,600 max Tokens reserved for the generated answer. No. Long answers are a separate decision.
Rule of thumb. A good chat window is prompt + retrieved evidence + output budget + safety margin. It is not “one window per conversation turn”. If conversation history is needed, compress it; do not multiply the window by the number of turns.

3. How large a window fits on this machine

KV-cache cost of this model

Ollama reserves the KV cache for the entire configured window when it loads the model. For a conventional transformer: 

KV bytes per token =
  2 (key and value)
  × layers
  × KV heads
  × (key length + value length)
  × bytes per element

For ornith-1.5:35b:
  2 × 41 × 2 × (256 + 256) × 2 bytes
  = 83,968 bytes/token
  ≈ 82 KiB/token
  ≈ 1.28 GiB at 16,384 tokens

That estimate matches the observed 21 GB: roughly 19.7 GB of weights plus 1.3 GiB of KV cache. The model metadata also exposes a hybrid/MoE/SSM architecture (full_attention_interval = 4), but the measured total is consistent with the full 41-layer KV estimate, so this document uses the conservative figure.

Ollama charges for the whole window. A 64k setting reserves roughly 5.1 GiB of KV cache even if every question is short. This is why “set it to the model maximum” is not free. Verify the actual allocation with ollama ps (CONTEXT and PROCESSOR columns), not just the model card.

Why 32k is the sweet spot here

  • It is enough. The designed maximum working set is about 8k of evidence plus roughly 2–3k of instructions and prompt scaffolding plus up to ~1.6k of output. That is ~12–13k, leaving substantial room for a long user question, code, or a larger retrieved set. Default-depth turns use much less evidence and are smaller still.
  • It is cheap. Moving from 16k to 32k adds about 1.3 GiB of KV cache, less than 6% of the current resident footprint.
  • It does not slow normal answers much. The model only attends to the tokens actually present in the prompt. A 32k window with a 12k prompt costs the same attention work as a 32k window with a 12k prompt; the larger window mainly reserves memory and permits longer prompts. Prefill grows with the prompt, not with the reservation.
  • It stays on the GPU. At roughly 22 GB on a 36 GB unified-memory machine, the model remains fully GPU-resident with room for macOS and normal applications. Crossing into CPU spill destroys generation speed.

When 16k is still the right answer

If the priority is minimum memory and maximum stability, keep 16,384. The current application is designed around an 8,192-token evidence budget, and 16k is enough for that plus prompt and output. The practical difference between 16k and 32k is headroom, not baseline answer quality. A reasonable policy is:

  • 16k on a 24–32 GB machine or when other applications are memory-heavy.
  • 32k on this 36 GB machine (recommended).
  • 24,576 as a conservative middle ground if 32k shows memory pressure.

4. Why a larger window is not automatically better

The model advertises 262,144 tokens, but advertised maximum context and useful context are different quantities. Recent research consistently finds that models use long contexts unevenly and that longer inputs can degrade reasoning even when retrieval is perfect.

Evidence from the literature

  • Effective context is often much shorter than the advertised window. “Why Does the Effective Context Length of LLMs Fall Short?” finds that many open models have effective context lengths below half of their training length, driven by a left-skewed distribution of relative positions seen during training (arXiv:2410.18745).
  • RULER measured effective context lengths well below claimed lengths across many long-context models (Hsieh et al., 2024, arXiv:2404.06654).
  • “Context length alone hurts.” A 2025 controlled study found 13.9%–85% performance degradation as input length increased, even when the model could retrieve all relevant evidence perfectly and even when distractor tokens were masked. The authors recommend a retrieve-then-solve pattern that turns a long-context task into a short-context one (arXiv:2510.05381).
  • Lost in the middle. Models often attend more reliably to the beginning and end of a long input than to the middle (Liu et al., 2023, arXiv:2307.03172). Later work shows the effect is strongest while inputs occupy up to about 50% of the window, after which a distance-based bias dominates (arXiv:2508.07479).
  • Context rot / attention budget. Anthropic’s 2025 context engineering guidance describes context as a finite resource: as tokens grow, recall degrades, and the best strategy is the smallest set of high-signal tokens. It recommends compaction, structured note-taking, and sub-agents for long-horizon work rather than stuffing everything into one window (Anthropic, “Effective context engineering for AI agents”, 2025-09-29).
  • Maximum effective context is task-dependent. A 2025 study (“Context Is What You Need”, arXiv:2509.21361) found that maximum effective context windows were drastically smaller than advertised and shifted by problem type; some top models degraded with as little as a few hundred tokens of context.
Implication for this application. The current design is already aligned with the research: it retrieves a focused evidence set, writes from that evidence, and uses the conversation only to resolve references. The correct response to long conversations is not “make the window 128k”; it is “keep the per-turn working set small and curate memory”.

What “32k” should mean in practice

  • 32k is the ceiling, not the target. Keep the evidence budget at 8k. Do not increase depth just because the window is larger.
  • Place high-value evidence near the end of the prompt. Retrieval results should be immediately before the question. The system prompt and stable instructions belong at the beginning.
  • Keep the answer request short. A verbose prompt consumes the same attention budget as evidence.
  • Use list mode only for genuine list questions. List answers may use the full 8k evidence budget; normal questions should stay smaller.

5. Managing long conversations

Assessment of the current approach

The current server-side 8-turn conversation with follow-up rewriting is a good foundation. It avoids the most common failure mode of naive chat applications, where the entire transcript is pasted into every prompt and prompt size grows linearly with session length.

Its limitations are:

  • After 8 turns, older facts are simply dropped. A user who said “my trip is in Sapporo in February” twenty turns ago may have to repeat it.
  • Each prior answer is truncated to 900 characters, which can drop a crucial detail.
  • There is no persistent memory across server restarts or sessions.
  • There is no explicit summary or “known facts” block, so follow-up rewriting is the only consumer of history.

Recommended memory architecture

TierWhat it containsApprox. budgetHow it is used
Tier 0: current turn The user's question, rewritten into a standalone retrieval question. < 200 tokens Drives BM25 retrieval and the answer prompt.
Tier 1: recent turns Last 4–6 user/assistant turns, answers truncated to ~400–600 characters. 400–1,000 tokens Resolve pronouns, ellipsis, and near-term follow-ups.
Tier 2: running summary A compact, structured summary of older turns: entities, decisions, preferences, unresolved questions, references. 300–800 tokens Preserves continuity without replaying the transcript.
Tier 3: long-term memory Durable facts stored outside the window (SQLite FTS5, JSONL, or a small vector index). Retrieved on demand. Top 2–3 entries, < 500 tokens Cross-session recall: user preferences, recurring topics, saved decisions.
Recommended shape. For each answer, build the prompt from: stable system instructions + retrieved evidence (8k) + recent 4–6 turns or summary (≤1k) + current question. Keep total input around 10–12k at most (usually less at the default depth). Reserve the remaining 32k window as headroom, not as a reason to add more history.

Compaction policy

Summarization research converges on a two-threshold design: compact when the session crosses a “fill line”, and reduce to a lower “drain line” so compaction is not triggered on every turn. Factory’s 2025 write-up describes this as T_max (compression threshold) and T_retained (target after compression), and recommends updating the summary incrementally rather than re-summarizing the whole transcript each time. LangMem’s summarize_messages follows the same pattern: a running summary plus recent messages.

A practical policy for this application:

  • Keep the last 4–6 turns verbatim.
  • Compact when the conversation has more than 12 turns, or when the estimated conversation-memory block exceeds 1,200 tokens.
  • After compaction, keep the running summary plus the last 4 turns. Do not repeatedly summarize the entire history; summarize only the newly evicted turns and merge them into the existing summary.
  • Cap the summary at 600–800 tokens. If it grows beyond that, move durable facts to Tier 3 and drop procedural chatter from the summary.
  • Never summarize away explicit user requirements, names, dates, locations, preferences, decisions, or open questions.

What the summary should preserve

KeepDrop
Entities and aliases (“Terence Tao”, “Nijo Market”, “the Sapporo trip”) Small talk and acknowledgements (“thanks”, “okay”)
User constraints and preferences (“no shellfish”, “prefer trains”) Repeated restatements of the same fact
Decisions and conclusions (“we chose the 90-day visa”) Raw tool output and duplicate retrieved chunks
Open questions and next steps Speculative reasoning that was not adopted
References needed to re-retrieve details (URLs, IDs, section names) Exact wording of long answers

Summarization model choice

Use the small helper model (chat.CHAT_MODEL, the 1.7B LFM3 artifact) for compaction. It is already resident, fast, and cheap. Reserve ornith-1.5:35b for the answer. Summarize with a strict prompt: 

Summarize the conversation turns below for future retrieval.
Preserve only:
- names, places, dates, and entities
- user preferences and constraints
- decisions and conclusions
- open questions
- references needed to look up details again
Do not add facts. Do not add commentary.
Output at most 250 words, as short bullets.

Retrieval over memory, not transcript stuffing

For long-term memory (Tier 3), store each compact memory as a short record and retrieve the top 2–3 records by BM25 or a small embedding index. This is the same principle as the application's existing evidence retrieval. It keeps the prompt bounded and makes memory scale with the number of relevant facts, not the number of turns.

Related research: MemGPT treats the context window as “main memory” and pages information to external storage (arXiv:2310.08560); MemoryBank applies forgetting-curve and importance-based retention (arXiv:2305.10250); the Context Engineering survey catalogues memory hierarchies, compression, and retrieval as the main tools for long-horizon interactions (arXiv:2507.13334).

Prompt caching and layout

Ollama reuses the KV cache for an identical prompt prefix. Keep the stable instructions at the very beginning and put variable content (retrieved evidence, current question) at the end. Avoid changing the system prompt or the order of static sections per turn; that invalidates the cache and raises time-to-first-token.

Do not put the entire conversation at the beginning of the prompt. It is both expensive and the least useful material for the current question.

Anti-patterns

  • “Just use 128k and keep everything.” Memory cost, prefill cost, and context-rot risk all rise; answer quality does not improve proportionally.
  • Re-summarizing the entire history every turn. Cost grows linearly and the summary drifts. Summarize only newly evicted turns.
  • Over-compression. Dropping details too aggressively forces the model to re-ask or re-fetch; keep breadcrumbs (IDs, names, URLs).
  • Putting raw retrieved chunks into the permanent summary. Retrieve them again when needed.
  • Using a large window as a substitute for retrieval quality. A larger window with irrelevant evidence is worse than a smaller window with the right evidence.

def record_turn(question, resolved_question, answer):
    self.conversation.append({...})

        self.compact_conversation()

def compact_conversation():
    keep = self.conversation[-CONVERSATION_RECENT_TURNS_AFTER_COMPACT:]
    evicted = self.conversation[:-len(keep)]

8. Verification and benchmarks

Memory and latency checks

  1. After changing ANSWER_NUM_CTX to 32768, restart the server and run ollama ps. Confirm CONTEXT = 32768 and PROCESSOR = 100% GPU. Expected resident size: ~22–23 GB.
  2. Ask one short question and check /benchmark: prompt tokens should remain near the current value (the retrieval budget did not change); time-to-first-token should be within roughly 10% of the 16k baseline.
  3. Ask a long, 3,000–4,000-token question or paste a long code block. Confirm the prompt fits without truncation and the answer still streams.
  4. Run a 30-minute session and watch memory and swap. If macOS memory pressure rises or ollama ps shows a CPU/GPU split, fall back to 24,576 or 16,384.

Conversation-quality tests

TestWhat to check
Long-range fact recall State a fact in turn 1 (“my trip is in Sapporo in February”), talk about something else for 15–20 turns, then ask “what did I say about my trip?”. The summary/memory should recover it without the full transcript.
Pronoun resolution across compaction Use “he/she/it/that place” after the original turn has been summarized. The rewritten standalone question should still name the correct entity.
Topic switch Ask about an unrelated subject after a long thread. The existing unrelated-question reset should still fire and not inherit stale context.
Summary drift After several compactions, ask about an early decision. The summary should preserve the decision even if wording changes.
Memory budget Verify summary tokens stay ≤700 and recent turns stay ≤1,000. Total conversation material should stay around 1–2k, not grow with turn count.
Retrieval quality Compare answer correctness at depth 12 and 8k evidence before and after adding memory. Memory must not displace evidence.

Suggested A/B benchmark

Compare num_ctx = 16384, 32768, and 65536 on the same prompts. Record:

  • resident memory and whether the model stayed 100% GPU;
  • prompt tokens, prefill time, TTFT, and total answer time;
  • answer correctness on 20–30 representative questions (including list and code questions);
  • long-conversation fact recall and topic-switch behavior.

Expected result: 16k and 32k should be nearly identical on normal questions; 32k should be strictly better only when the prompt genuinely exceeds 16k. 64k is unlikely to improve normal chat and will cost memory and some latency.

  • The 32k/64k/128k memory figures are calculated from the model metadata and calibrated against the 16k measurement; they are not direct measurements.
