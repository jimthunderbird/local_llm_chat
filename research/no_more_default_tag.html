Auto-Selecting Soft Tags Instead of Defaulting to japan

Research note for the local RAG chatbot. Question: can the chat choose the relevant soft tag(s) from the question instead of opening with the default japan tag, and would that be slower or use more memory?

1. Executive answer

Yes, the feature is feasible, and it is a good idea. But the important detail is that the chatbot already keeps one global trunk corpus in memory and treats every tag as a query-time soft scope. The default japan tag is not a corpus partition. Therefore the proposed change is primarily a routing change, not a loading change.
~0.08–0.17 s Measured lexical tag-routing cost per question on the current 11,141-trunk corpus. This is the direct added cost if the route is computed from the question.
+0 to a few MiB Memory cost if routing selects from the already-loaded global corpus. The corpus and BM25 index stay exactly as they are today.

If "load related trunks" means physically load only the trunks that belong to the selected tag, memory can drop a lot: the current global retrieval state costs about 67 MiB traced (about 128 MiB process peak RSS), while a lexical japan subset costs about 8.4 MiB traced. But that version is not recommended as the default: soft tags overlap, many questions span tags, tag membership is not canonical, and the retrieval corpus is tiny compared with the Ollama models. Reloading per question would also add BM25 rebuild latency and make routing mistakes much harder to recover from.

The net effect on latency is likely neutral to positive: tag selection adds roughly one BM25 pass plus a small tag-ranking computation (and, if used, one small-model call), but it can avoid the much more expensive cross-tag fallback loop, where each wrong tag costs another retrieval, filter, and answer-generation attempt.

2. What the current implementation actually does

The current design is already close to the requested behavior, with one deliberate shortcut: it starts with a default tag instead of selecting a tag from the question.

  • One global corpus. chat.load_chunks() loads every learned *.trunk file into one list. Tags do not own files or partitions any more. The startup path in app/chat_server.py builds one BM25 index for that global list before accepting requests.
  • Tags are descriptions. tags.toml is a registry of tag names and natural-language descriptions. A tag is a query-time scope, not a hard filter over a separate corpus.
  • Default tag. chat.DEFAULT_TAG = "japan" and the server starts with --tag japan. The first answer attempt therefore uses the japan profile as the soft scope.
  • Question-level retrieval is already global. BM25 scores every loaded trunk, not only the current tag's trunks. The tag is applied afterward by chat.tag_filter_candidates() and/or the cheaper lexical lexical_tag_scope().
  • Cross-tag fallback already exists. If the default tag cannot answer, ChatState.fallback_tag_order() calls chat.rank_tags_for_question() to rank other tags and retries them one by one. This is effectively a post-hoc version of the requested feature, but it runs only after a failed answer.
Consequence: "based on the question, examine the existing soft tags, then load the related trunks" can be implemented without changing the corpus-loading architecture at all. The relevant trunks are already loaded; the work is to decide which tag profile(s) should scope the current question, and to do that before the first answer attempt.

5. Speed impact

5.1 Added work

  • Lexical routing: one top-40 BM25 pass over the global index plus scoring 13 tag descriptions over the top 10 candidates. Measured at 77–165 ms. The global BM25 index already exists, so this does not rebuild anything.
  • Optional small-model routing: if the router asks qwen3:1.7b to choose a tag from the question and/or a few snippets, add one short generation call. The existing tag-scope filter already uses this model and runs in candidate batches of up to 20. Reusing one ranking/classification call is much cheaper than the multi-round answer path.
  • No per-question corpus load or index rebuild in interpretation A. The expensive 1.74 s BM25 build stays a startup cost.

5.2 Work that can be removed

  • Wrong-tag first attempts. Today a question outside japan first retrieves and filters under japan, then may fail, then enters the cross-tag fallback loop. Auto-routing can choose the right scope on the first attempt.
  • Repeated fallback retrieval. Each fallback tag currently costs another retrieval/filter/answer attempt. The code reuses tag-independent iterative evidence across tags, but tag filtering and generation still repeat. Removing even one fallback attempt saves far more than the 0.1–0.2 s routing overhead.
  • User time spent choosing a tag manually. With an auto mode, the user no longer has to know whether a question is "japan" or "retire", which matters for questions that straddle tags.

5.3 Expected latency shape

ScenarioCurrentWith auto-routingNet

Question clearly outside japan Wrong-tag attempt, then cross-tag ranking, then retry Correct tag on the first attempt Likely faster
Question spans two tags May fail in the first tag and fall back Union of top-2 tags can succeed immediately Likely faster and more accurate
Out-of-corpus question Try default tag, then ranked fallbacks Low-confidence route can go straight to global/unscoped retrieval Faster; fewer wasted model calls
Router is wrong n/a First attempt fails, then existing fallback still recovers Adds routing cost to the current cost
In short: auto-routing is not inherently slower. It adds a small, bounded front-end cost and can remove a large, variable tail cost. The worst case is a wrong route plus the existing fallback; the common case is near the baseline and the cross-tag case improves.

6. Memory impact

6.1 Interpretation A: keep the global corpus

The one-time global corpus is already required for cross-tag fallback and for questions that do not cleanly belong to one tag. Auto-routing adds only:

  • a small score table with one float per tag per question (KBs),
  • a bounded route cache keyed by normalized question (KBs to low MBs if capped),
  • no duplicate chunk list and no duplicate BM25 index.

Measured retrieval state is 9.8 MiB of chunks plus 56.7 MiB of BM25 index, with a 67 MiB traced peak and a 128.4 MiB process peak RSS. The routing layer is negligible against those numbers.

6.2 Interpretation B: physically load only related trunks

The memory saving is real but bounded. For the lexical japan subset, the retrieval state drops from ~67 MiB traced to ~8.4 MiB traced. The ai_math subset is larger, and unions of tags grow toward the global corpus. The trade-offs are:

  • You cannot know the right tag without examining the corpus first. A router that inspects tag descriptions and top question matches needs either a global index or a precomputed tag-membership index. The latter costs memory of its own.
  • Soft tags overlap. A hard partition misclassifies boundary paragraphs, and the existing design deliberately lets one video contribute evidence to several tags.
  • Multi-tag questions need a union. "Compare Rust and Go" or "retiring in Japan" may need two or more scopes. Loading and unloading per question adds complexity for little gain.
  • The model is the memory giant. ornith-1.5:35b and even qwen3:1.7b live in separate Ollama processes and are measured in gigabytes. Shaving tens of MiB from the Python retrieval process is not where memory pressure comes from.

6.3 Interpretation C: precomputed hard tag corpora

Because the tag definitions are semantic and overlapping, a hard assignment either loses recall or duplicates trunks across tags. Duplicating a large fraction of an 11k-trunk corpus across several tags can use more memory than one shared global corpus, and it turns a routing mistake into a permanent blind spot.

7. The real risk is routing accuracy, not cost

The current lexical router is a useful first pass, but it is not accurate enough to be the sole basis for removing the default tag. In a quick measurement with query expansion disabled, rank_tags_for_question returned:

QuestionTop-ranked tags (first four)Assessment
where is nijo market trade_school_job_program_bubble, japan, php, retire Wrong top-1 Japan is only second.
what are all levels of wagyu japan, php, artificial_intelligence, ai_and_coding Correct top-1
show me code to implement binary search in rust rust, golang, ai_and_coding, php Correct top-1
did terence tao write a new book ai_math, math, ai_math_coding, artificial_intelligence Correct top-1
how do i retire in japan ai_and_coding, programming_software, japan, ai_math_coding Japan is third A mixed-tag question.

Why this happens: the router scores tag descriptions against the question and the top question-matching chunks. A chunk about Nijo Market may match the question very well but not contain the literal words "Japan" or "Japanese", so the japan description gets weak coverage. Conversely, a broad tag such as ai_and_coding contains many terms and can match incidental words. This is a description-calibration problem, not a reason to abandon the idea.

Do not simply delete the default tag and trust the existing lexical router. That would regress common questions such as "where is nijo market" and "how do i retire in japan". Use a hybrid router, keep top-k and an unscoped fallback, and evaluate it before changing the default.

8. Recommended design

8.1 Keep the global corpus and index

Keep one loaded corpus and one BM25 index. This preserves cross-tag recall, avoids per-question rebuilds, and makes the memory cost of routing negligible.

8.2 Introduce an auto scope, not "no tag"

Replace the startup default with an explicit auto mode:

  • /tag auto and a status value such as soft tag auto → japan after routing.
  • --tag japan and /tag japan remain available as manual overrides.
  • auto should be able to resolve to global (no tag filter) when no tag is confident, rather than forcing a weak tag.

8.3 Hybrid tag router

  1. Run the normal question normalization and retrieval once. Reuse the BM25 index and, if available, the cached query expansion.
  2. Score each tag with several weak signals:
    • BM25 similarity between the question and the tag description,
    • lexical coverage of the tag's distinctive terms in the top question-matching chunks,
    • video-level evidence: if a video is strongly associated with a tag, boost all of that video's chunks (the current code already restores video scope after tag filtering),
    • conversation context: a follow-up in a japan conversation should keep japan unless the question clearly changes topic.
  3. Optionally ask qwen3:1.7b to choose from the top 3–5 candidate tags, given the question and compact tag descriptions. Use a strict multiple-choice prompt and a short output budget. This is the same model already used for query expansion and candidate filtering, so it is normally warm.
  4. Select the top tag when its score is clearly above the runner-up; otherwise keep the top 2 or return global. Multi-topic questions should use the union of their top tags, not a forced single choice.
  5. Apply the existing tag scope filter to the selected union. If the union fails to answer, the existing cross-tag fallback remains as a safety net and can be ordered using the router's scores.

8.4 Caching and conversation behavior

  • Cache the route by normalized question and tag-registry version. The existing query-expansion cache and answer cache already establish this pattern.
  • For follow-ups, bias toward the active resolved tag. A follow-up such as "what about in winter?" should not reroute to an unrelated tag because the pronoun-heavy question has weak lexical evidence.
  • Reset the route when the user explicitly changes tags, transcripts, or articles.

8.5 Do not unload the corpus per question

If memory ever becomes a measured problem, add an optional per-tag index cache with an LRU bound. Do not load and discard trunks on every question. The measured full-corpus load is only 0.10 s, but rebuilding BM25 is 1.74 s, and routing already needs global evidence to make a good decision.

9. Evaluation plan and acceptance criteria

Build a small, fixed evaluation set before changing the default. Include clearly single-tag questions, mixed-tag questions, follow-ups, and out-of-corpus questions.

The measurement harness can reuse the existing benchmark hooks and the retrieval timings already collected in stats. Capture per-question route decisions so misroutes can be inspected offline rather than guessed from answer text.

10. Verdict

Feasible? Yes. The corpus is already global and the tag system is already soft, so this is a routing addition rather than a new storage architecture.

Slower? Not materially. The measured lexical routing cost is about 0.08–0.17 s per question on the current corpus. A small-model routing call adds a short, bounded generation. The routing cost is often repaid by avoiding a wrong-tag attempt and the cross-tag fallback loop.

More memory? No, for the recommended query-time scoping design: routing needs only a small score table and optional cache while the existing global corpus and index remain shared. Physically loading only related trunks can save roughly tens of MiB, but that is small compared with the model processes and introduces overlap, multi-tag, rebuild, and routing-error problems.

Main caveat? The current lexical router is not accurate enough by itself. The implementation should use a hybrid router, keep the top-k tags, support a global fallback, bias follow-ups toward the active tag, and retain the existing cross-tag fallback. With those safeguards, removing the hard-coded japan default is reasonable.

11.2 Pseudo-code

def resolve_scope(state, question, conversation):
    # Manual overrides win.
    if state.tag != AUTO:
        return [state.tag]

    # Follow-ups keep the active tag unless the topic clearly changes.
    if conversation.has_recent_scope() and question_is_follow_up(question):
        return [conversation.active_tag]

    candidates = rank_tags_for_question(question, state.global_chunks, limit=5)
    scored = score_tag_descriptions(question, candidates)      # BM25 + overlap
    if needs_tie_break(scored):
        scored = ask_small_model_to_choose(question, scored[:5])

    top = choose_top_k(scored, max_k=2, confidence_threshold=...)
    if not top:
        return [GLOBAL_SCOPE]                                  # no tag filter
    return top

# In _run_question:
scopes = resolve_scope(state, retrieval_question, state.conversation)
answer = attempt(scopes, state.global_chunks)
if answer_is_insufficient(answer):
    answer = existing_cross_tag_fallback(...)                  # safety net

11.3 Operational notes

  • Show the resolved scope in /status and the status bar, for example auto → japan or auto → global, so a misroute is visible and the user can override it.
  • Keep --tag japan working for repeatable benchmarking and for users who want a fixed scope.
  • Include auto in tab completion and in the command help text.
  • Add routing metrics to the benchmark output: chosen tags, router score, whether the answer needed fallback, and route decision time.
  • Version the route cache with the tags.toml signature, just as the tag loader already invalidates on file changes.

All measurements in this note were taken from the current checkout (app/chat_server.py, chat.py, tags.toml) with the full local corpus of 11,141 trunks from 519 videos. Timings vary with machine load and Ollama residency; the memory and routing order-of-magnitude conclusions are stable.
