Making /youtube search feel instant

Research note for local_llm_chat · 2026-11-04 · scope: app/chat_server.py (_command_youtube_search, _run_youtube_search), search_youtube.py, and the videos SSE event in app/chat.html.

Question. /youtube search "<words>" works, but the video cards take a long time to appear. Where does the time actually go, and what is the fastest safe way to show cards in the chat?

1. TL;DR

The current command does far more network work than the UI needs before it renders anything. In a measured run of the exact production arguments, it took 31.7 s end to end. ~70% of that was one phase: fetching the upload date of up to 40 candidates, one watch-page extraction at a time.

Search 100 candidates 6.5 s
Fetch 40 upload dates 23.0 s
Verify English captions 3.4 s
Recommended path. Remove the per-video date enrichment from the critical path, shrink the candidate pool, verify captions only for the shortlist (in parallel, with a deadline), and stream cards to the UI in batches. The same existing libraries already reach ~3.7 s with a 24-candidate pool and a 12-way caption check; a direct InnerTube search response can bring the first cards down to ~1–2.5 s, with dates and caption checks filling in afterwards.

3. Current pipeline, step by step

The path from pressing Enter to seeing cards is:

  1. UI → server. The command handler (app/chat_server.py:5953) emits a text line and calls _cached_youtube_search(keyword, 7) (:6086).
  2. Server → subprocess. _run_youtube_search() (:6010) spawns search_youtube.py with --json --limit 7 --min-duration 300 --max-duration 2400 --any-date --sort-recent and waits for the process to finish (subprocess.run, 180 s timeout).
  3. Search. search_videos() (search_youtube.py:226) builds playlistend = max(limit × 10, 100) (:248) and asks yt-dlp for flat results. Because --any-date is set, _search_url(..., within_year=False) (:86) omits the sp filter entirely.
  4. Duration filter. Entries are kept only if ie_key == "Youtube", duration is known, and 300 ≤ duration ≤ 2400 (:262–278). In the measured run, 100 entries produced 59 eligible videos.
  5. Date enrichment. In recent mode, _enrich_upload_dates() (:173) fetches exact upload dates for the first 40 videos with DATE_ENRICH_LIMIT = 40 and 8 workers, using a full yt_dlp.extract_info(watch_url) per video (:154).
  6. Sort. Videos are sorted newest-first by timestamp (:303–311). This is why the enrichment exists: flat search results do not include upload dates.
  7. Caption verification. _with_english_transcripts() (:196) checks candidates in batches of max(limit×2, 12)=14, 8 workers, calling YouTubeTranscriptApi().list() (has_english_transcript, :110). It stops when limit videos pass.
  8. Server → UI. Only after the subprocess exits does the server emit one videos SSE event (:6000–6008). app/chat.html:5544 replaces entry.videos and renders all cards at once.

4. Why each phase is slow

4.1 Date enrichment dominates (23 s)

_fetch_upload_date() uses yt-dlp to extract a full watch page just to read one field. That is expensive even with skip_download: yt-dlp fetches the watch page, the player response, and may process JavaScript/format metadata before returning. Measured at ~3.0–3.6 s per video. With 8 workers and 40 videos, the phase is five sequential waves: ~18–23 s.

Worse, the date is only needed for ordering and for a small label on each card. All 40 fetches are done even though the UI shows six cards.

4.2 The candidate pool is 4–14× larger than needed (6.5 s)

CANDIDATE_MULTIPLIER = 10 and MIN_CANDIDATES = 100 (:63–64) mean a request for 7 videos walks five search-result pages. Each page is ~0.76–1.0 s, so the pool alone costs 4–6 s. For a “most recent” search, 24–40 candidates is normally enough to survive duration filtering.

4.3 Caption checks are serialised into the critical path (3.4 s)

The “every returned video must have English captions” guarantee is enforced before rendering. That is a reasonable product rule, but it does not have to be a blocking rule. youtube-transcript-api needs ~1–1.6 s per lookup (network round-trip to the player endpoint). Parallelism helps (6 checks: 5.98 s serial → 1.23 s parallel), but the current batch size and the fact that the UI waits for all of it add seconds.

Hidden failure mode. has_english_transcript() catches every exception and returns False (search_youtube.py:117–127). On a blocked cloud IP (see avoid_ip_blocking.html), every candidate looks captionless, so the batch loop keeps scanning and may eventually return fewer than 6 videos — or none. In that case the command is both slow and wrong. Treat “lookup failed” differently from “no English track”.

4.4 The UI cannot render progressively

_run_youtube_search() waits for the subprocess, parses all JSONL, normalises every item, returns a list, and then sends one videos event. Nothing is painted until the slowest phase finishes. Even with a perfect backend, the perceived latency is the sum of all phases.

4.5 Subprocess and repeated work

The subprocess costs only ~0.13 s here (imports are warm), so it is not the main problem. But it also means:

  • The cache is only in memory (self.state.youtube_search_cache, chat_server.py:3679) and dies with the server.
  • “More” re-runs the whole search if the cache does not already hold enough results (:6086–6107).
  • Concurrent identical searches can duplicate all of the work (no single-flight lock).

6. Target design

Split the command into a fast path that answers the user and a background enrichment path that does not block rendering. 

Enter
  │
  ├─ cache hit? ── yes ──► emit cached cards immediately (stale-while-revalidate)
  │
  └─ no
      │
      ├─ InnerTube search (1 page, videos+This-year filter, 20 items)   ~0.8–1.0 s
      │     └─ parse videoRenderer: id, title, length, channel, thumb,
      │        publishedTimeText (relative), viewCount
      │
      ├─ duration filter 5–40 min client-side (free)
      │
      ├─ emit first batch of 6 cards  ────────────────────────────────► UI paints
      │
      ├─ caption verify first 12 in parallel, 1.5–2 s deadline
      │     └─ emit updated batch (verified:true/false) ──────────────► badges settle
      │
      └─ optional: exact dates for visible 6, background, cache 30 d ─► emit update

What to show when exact dates are unavailable

InnerTube returns relative strings such as "3 weeks ago", "5 months ago", and "1 year ago". These are enough for “most recent” ordering and are honest in the UI. Convert them to an approximate age (minutes/hours/days/weeks/months/years) for sorting; keep the original string for display. Only fetch exact upload_date for cards that are actually visible, and only if the UI needs it.

7. Implementation sketches

7.1 Direct InnerTube search (fast, includes relative dates)

import requests

INNERTUBE_SEARCH = "https://www.youtube.com/youtubei/v1/search?prettyPrint=false"
# Videos only + "This year" upload filter. Verified live 2026-11-04.
PARAMS_VIDEOS_THIS_YEAR = "EgQIBRAB"
CONTEXT = {
    "client": {
        "clientName": "WEB",
        "clientVersion": "2.20240401.00.00",
        "hl": "en",
        "gl": "US",
    }
}

def _walk(obj, key):
    if isinstance(obj, dict):
        for k, v in obj.items():
            if k == key:
                yield v
            yield from _walk(v, key)
    elif isinstance(obj, list):
        for item in obj:
            yield from _walk(item, key)

def _runs_text(node):
    if not node:
        return ""
    if "simpleText" in node:
        return node["simpleText"]
    return "".join(run.get("text", "") for run in node.get("runs", []))

def _parse_length(text):
    # "13:59", "1:05:53", "45" -> seconds
    if not text:
        return None
    try:
        parts = [int(p) for p in text.split(":")]
    except ValueError:
        return None
    seconds = 0
    for part in parts:
        seconds = seconds * 60 + part
    return seconds

def innertube_page(session, keyword, params=PARAMS_VIDEOS_THIS_YEAR):
    """Return (videos, next_continuation_token)."""
    body = {"context": CONTEXT, "query": keyword, "params": params}
    data = session.post(INNERTUBE_SEARCH, json=body, timeout=6).json()

    videos = []
    for renderer in _walk(data, "videoRenderer"):
        vid = renderer.get("videoId")
        if not vid:
            continue
        thumbs = renderer.get("thumbnail", {}).get("thumbnails") or []
        videos.append({
            "id": vid,
            "title": _runs_text(renderer.get("title")),
            "channel": _runs_text(renderer.get("ownerText")),
            "duration": _parse_length(_runs_text(renderer.get("lengthText"))),
            "thumbnail": thumbs[-1]["url"] if thumbs else "",
            "published_text": _runs_text(renderer.get("publishedTimeText")),
            "url": f"https://www.youtube.com/watch?v={vid}",
        })

    token = next(iter(_walk(data, "continuationCommand")), {}).get("token")
    return videos, token

def innertube_continuation(session, token):
    body = {"context": CONTEXT, "continuation": token}
    data = session.post(INNERTUBE_SEARCH, json=body, timeout=6).json()
    videos = []  # same videoRenderer parsing as above
    ...
    next_token = next(iter(_walk(data, "continuationCommand")), {}).get("token")
    return videos, next_token

Notes: response is large (~600 KB uncompressed, ~80 KB gzip); let requests negotiate gzip. InnerTube is undocumented, so keep the current yt-dlp path as a fallback and pin/rotate the client version.

7.2 Relative-date parsing for ordering

import re
from datetime import datetime, timedelta, timezone

_UNIT = {
    "second": 1, "minute": 60, "hour": 3600, "day": 86400,
    "week": 7 * 86400, "month": 30 * 86400, "year": 365 * 86400,
}

def relative_age_seconds(text):
    """'3 weeks ago' -> 1814400; unknown -> None."""
    m = re.match(r"(\d+)\s+(second|minute|hour|day|week|month|year)s?\s+ago", text or "")
    if not m:
        return None
    return int(m.group(1)) * _UNIT[m.group(2)]

def sort_newest_first(videos, now=None):
    now = now or datetime.now(timezone.utc)
    def key(pair):
        index, video = pair
        age = relative_age_seconds(video.get("published_text"))
        if age is None:
            return (0, -index)          # unknown dates last
        return (1, -age, -index)        # smaller age = newer
    return [v for _, v in sorted(enumerate(videos), key=key, reverse=True)]

7.3 Caption verification with a deadline

import time
from concurrent.futures import ThreadPoolExecutor, as_completed

def verify_captions(video_ids, api, deadline_s=2.0, workers=16):
    """Return {video_id: True/False/None}; None means 'not checked in time'."""
    results = {vid: None for vid in video_ids}
    if not video_ids:
        return results
    pool = ThreadPoolExecutor(max_workers=min(workers, len(video_ids)))
    futures = {pool.submit(has_english_transcript, vid, api): vid
               for vid in video_ids}
    end = time.monotonic() + deadline_s
    try:
        for future in as_completed(futures, timeout=max(0.0, end - time.monotonic())):
            vid = futures[future]
            try:
                results[vid] = future.result()
            except Exception:
                results[vid] = None
    except TimeoutError:
        pass
    finally:
        pool.shutdown(wait=False, cancel_futures=True)
    return results

Change has_english_transcript() to return three states internally (True / False / Unknown) so a network error does not masquerade as “no captions”. Only False should remove a card; Unknown can stay with a neutral badge.

7.4 Progressive SSE

The frontend already replaces entry.videos on every videos event (app/chat.html:5544–5552), so the server can emit the same event multiple times with an accumulated, stable list. No protocol change is strictly required. 

# app/chat_server.py — inside _command_youtube_search
def emit(items, *, pending, verified_count, has_more):
    self._sse("videos", {
        "keyword": keyword,
        "items": items,
        "has_more": has_more,
        "pending": pending,              # optional UI hint
        "verified_count": verified_count,
    })

candidates = fast_search(keyword, limit=24)           # ~0.8–1.2 s
visible = candidates[:YOUTUBE_SEARCH_PAGE_SIZE]
emit(visible, pending=True, verified_count=0,
     has_more=len(candidates) > len(visible))

checks = verify_captions([v["id"] for v in candidates[:12]],
                         transcript_api, deadline_s=2.0)
verified = [v for v in visible if checks.get(v["id"]) is not False]
emit(verified, pending=False,
     verified_count=sum(1 for v in verified if checks.get(v["id"]) is True),
     has_more=len(candidates) > len(verified))

To avoid the “card disappears” effect, label pending cards with a subtle “checking captions…” note and only remove a card when the lookup definitively says there is no English track.

7.5 Persistent cache with stale-while-revalidate

import hashlib, json, os, tempfile, time
from pathlib import Path

CACHE = Path.home() / ".cache" / "local_llm_chat" / "youtube"
CACHE.mkdir(parents=True, exist_ok=True)

def cache_key(kind, *parts):
    raw = "\x1f".join(str(p) for p in parts)
    return CACHE / f"{kind}-{hashlib.sha256(raw.encode()).hexdigest()[:24]}.json"

def cache_read(path, ttl):
    try:
        data = json.loads(path.read_text(encoding="utf-8"))
    except (OSError, ValueError):
        return None
    if time.time() - data.get("created", 0) > ttl:
        return None
    return data

def cache_write(path, payload):
    payload = {**payload, "created": time.time()}
    fd, tmp = tempfile.mkstemp(dir=CACHE, suffix=".tmp")
    try:
        with os.fdopen(fd, "w", encoding="utf-8") as fh:
            json.dump(payload, fh, ensure_ascii=False)
        os.replace(tmp, path)
    finally:
        if os.path.exists(tmp):
            os.unlink(tmp)

7.6 Optional: YouTube Data API v3 path

# Two calls, exact metadata, no watch-page scraping:
# 1) search.list: 100 quota units, returns ids + publishedAt + thumbnails
GET https://www.googleapis.com/youtube/v3/search
    ?part=snippet&type=video&order=date&maxResults=50
    &q=rust+programming&key=$YOUTUBE_API_KEY

# 2) videos.list: 1 quota unit, up to 50 ids, returns duration + caption flag
GET https://www.googleapis.com/youtube/v3/videos
    ?part=contentDetails,snippet&id=ID1,ID2,...
    &key=$YOUTUBE_API_KEY
  • order=date is the supported exact-date ordering; this is what the web UI no longer offers.
  • contentDetails.duration is ISO-8601 (PT13M59S); parse to seconds and filter 5–40 min.
  • contentDetails.caption tells you captions exist, but not whether they are English. Keep a short transcript check for the final 6–12.
  • Quota: 101 units per uncached search; the default 10,000/day allows ~99 searches/day. Cache aggressively, or request a quota increase. Keep the key server-side (environment variable), never in chat.html.

9. Risks and trade-offs

RiskImpactMitigation
InnerTube is undocumented and changes without notice. Search breaks or returns empty. Keep yt-dlp as fallback; pin client version; add a smoke test that asserts ≥1 videoRenderer for a known query.
YouTube throttling / bot checks / IP blocks. Caption lookups fail, cards drop, searches slow down. Cap concurrency (8–16), add timeouts, distinguish Unknown from False, cache, and follow the IP-block playbook.
Relative dates are coarse (“1 year ago”). Ordering ties and less precise labels. Use relative text only for ordering; fetch exact dates lazily for visible cards or use Data API order=date.
Progressive caption checks can remove a card after it is shown. Jarring UI, possible duplicate layout shifts. Show “checking captions…” state, reserve card slots, only remove on definitive False.
Cache staleness. New uploads missing for the TTL window. Short search TTL (15–30 min), stale-while-revalidate, manual refresh on repeated searches.
Concurrent identical searches duplicate work. CPU/network spikes, rate limits. Single-flight per cache key; queue followers onto the first result.
Data API quota exhaustion. Search fails for the rest of the day. Cache, quota accounting, fall back to InnerTube/yt-dlp, keep the key server-side.

10. Validation plan

  1. Instrument the phases. Record t_search, t_filter, t_dates, t_verify, t_emit. Log to stderr when YOUTUBE_SEARCH_TIMING=1; optionally surface in /benchmark.
  2. Baseline. Run 10 distinct queries × 3 cold runs and 3 warm runs. Report p50/p95 for: time to first videos event, time to 6 visible cards, and “More” latency.
  3. Correctness checks for every returned video: duration in [300, 2400]; English caption verified; URL resolves; no duplicate ids; no Shorts/channels/playlists.
  4. Adversarial queries: “quantum physics lecture” (long videos), “japan travel 2026” (newsy/recent), “rust programming” (many old evergreen results), a query with almost no captioned results, and a query with zero results.
  5. UI checks: skeletons appear immediately; cards never reorder unexpectedly; “More” appends unseen videos; caption failures disappear cleanly; cached searches are instant.
  6. Regression guard: if InnerTube returns no videoRenderer, fall back to yt-dlp and log a warning instead of showing “no videos”.
