Working around YouTube transcript blocks on cloud IPs

Research note for local_llm_chat · 2026-11-04 · applies to fetch_youtube_transcript.py, fetch_youtube_transcript.php, youtube_video_learn.py and the /youtube learn flow.

Question. Transcript fetching works from a laptop but fails from the cloud with RequestBlocked, IpBlocked, HTTP 429, or Sign in to confirm you're not a bot. What are the practical ways around it, and which one should this repository adopt?

1. TL;DR

YouTube decides whether to serve captions per egress IP (plus session/client fingerprint). It blocks most IP ranges whose owner is a cloud provider, and it rate-limits the timedtext endpoint hard. No amount of retrying from the same address fixes an address-level block, and changing libraries (python API → yt-dlp → PHP port) does not either, because they all leave from the same IP.

Bottom line. Change where the request exits from, not which library makes it. For this repo: keep the existing Python/PHP fetchers, add (a) a residential egress path, (b) an env-var-driven proxy path with correct retry behaviour, (c) pacing + caching so we do not get rate-limited in the first place, and (d) a yt-dlp fallback. Do not make cookies or free proxies part of the design.

2. What is actually blocking us

The transcript API is not a public, documented endpoint. It reads the video watch page / InnerTube player response, finds the caption tracks, and then downloads a signed https://www.youtube.com/api/timedtext URL. Each of those steps is independently gated, which is why the same error message can mean different things.

Error taxonomy

SymptomReal causeWhat fixes it
IpBlocked / RequestBlocked / HTTP 429 on timedtext The egress IP has hit YouTube's rate limit or is on a cloud/datacenter range Different egress IP (residential), slower pace, caching
Sign in to confirm you're not a bot / LOGIN_REQUIRED / reCAPTCHA page Bot wall on the watch/player request; strongly correlated with datacenter and burned IPs Residential egress, valid client context/session; cookies only as a last resort
TranscriptsDisabled / empty caption list from a datacenter IP YouTube serves a 200 bot-check/consent page with no captionTracks; libraries misreport it as "disabled" Check playabilityStatus, not just the caption list; change egress
Metadata works, caption body is 0 bytes Missing browser TLS fingerprint / PO token; not an IP problem curl_cffi, JS runtime, correct player client (yt-dlp), or the Android/iOS InnerTube clients
429 that never clears after hours of idle Hard block on that IP, not a short window Rotate the IP; waiting does not help
Works for a few videos, then everything fails Per-IP volume limit (guest sessions are roughly a few hundred requests/hour) Pacing + jitter + spread over exits

Why a laptop works and a server does not

  • Hosting networks publish their address blocks; classifying them costs YouTube nothing. Consumer ISP addresses look like ordinary viewers.
  • A fresh VM has no cookies, no viewing history, and often no PO token provider — extra bot signals even before the IP is considered.
  • YouTube has tightened timedtext rate limits; one residential IP can also get blocked after a short burst.

3. Diagnose in five minutes

Run the same video from the failing host and from a residential connection. If it works at home, stop looking at the code — it is the address.

# 1. Which address does the failing host actually use?
curl -s https://api.ipify.org; echo
curl -s https://ipinfo.io/org

# 2. Minimal repro (Python library)
python -c "from youtube_transcript_api import YouTubeTranscriptApi as A; print(A().fetch('jNQXAC9IVRw')[:2])"

# 3. Same video through the PHP port
php fetch_youtube_transcript.php jNQXAC9IVRw

# 4. Is it the player response or the caption download?
#    A 200 watch page with no captionTracks = bot/consent page, not "captions disabled".
curl -s "https://www.youtube.com/watch?v=jNQXAC9IVRw&hl=en&gl=US" \
  | grep -o '"playabilityStatus":{"status":"[A-Z_]*"' | head -1

# 5. Does the residential IP work for the exact same video?
#    (run step 2 on the laptop / home machine)

Test video jNQXAC9IVRw ("Me at the zoo") is public, short, and has captions — a good canary. Pin a canary and run it after every change; a silent regression in the fetcher is otherwise indistinguishable from a block.

4. The options in detail

4.1 Use a residential egress you already own free best fit here

This project is a personal, local-first RAG tool. The simplest fix is to move the fetch step onto the same machine that already has a home connection — this working copy is on a Mac that is periodically online anyway. Two ways to expose it to a remote box:

  • Tailscale exit node / subnet router: join the cloud box and the home Mac to the same tailnet, then route only the fetcher through the Mac. Per-process, no global VPN needed.
  • SSH SOCKS tunnel: ssh -N -D 1080 home-mac, then point the fetcher at socks5h://127.0.0.1:1080. Easy to script, dies with the connection.
  • Fetch at home, sync the artifacts: run fetch_youtube_transcript.py on the Mac and copy .chat/youtube_transcripts/<id>.transcript and .title to the worker. The downstream steps (rewrite, trunks, embeddings) can run anywhere because they only call Ollama.

Limit: a home IP gets rate-limited too if a playlist backfill fires hundreds of requests. Pace it (section 5.4).

4.2 Rotating residential proxies paid recommended for cloud/bulk

The upstream library's own recommendation. The important details:

  • Residential, not "Static Residential" or "Proxy Server". Datacenter and static-residential exits get blocked just like the cloud host; the free Webshare tier uses Proxy Server and does not work.
  • Rotation per attempt, not per connection kept alive. A pooled connection pinned to one IP defeats rotation. Webshare's config sets prevent_keeping_connections_alive for this reason.
  • Retry actually matters. WebshareProxyConfig defaults to 10 retries when blocked. GenericProxyConfig defaults to 0 and keeps connections alive, so with another provider you must retry yourself and build a new client (new connection) per attempt.
  • Known bug: in youtube-transcript-api 1.2.4, Retry does not include POST in allowed_methods, so a 429 on the InnerTube player POST is not retried/rotated even with the Webshare config; only the GET paths benefit. A manual retry loop around fetch() covers this.
  • Bandwidth: residential proxies bill per GB. The player/watch pages cost roughly 0.3–0.4 MB compressed per video; caption payloads are small. If you later download audio, that dominates.
  • IPv4 vs IPv6: a whole IPv6 /64 is often treated as one reputation unit. Prefer IPv4 exits unless you know they are clean.

Recommended shape for this repo: read credentials from the environment (YT_PROXY_URL or WEBSHARE_PROXY_USERNAME/WEBSHARE_PROXY_PASSWORD), leave it unset by default so local runs stay direct, and layer a retry loop with jitter on top.

4.3 Hosted transcript APIs paid

The vendor fetches from its own network, so our IP never reaches YouTube. Typical pricing is $1–$10 per 1,000 transcripts, with free tiers of 50–100 credits. This is the lowest-effort option and a good escape hatch when the proxy path breaks during a YouTube change, but it adds an API key, a rate limit, and a dependency on someone else's scraper. Reasonable as an explicit fallback, not the primary.

4.4 yt-dlp + browser impersonation + PO tokens free

yt-dlp is a strong second implementation because it exposes the player-client and subtitle machinery directly:

  • --skip-download --write-subs --write-auto-subs --sub-langs en --sub-format vtt grabs only the captions.
  • Datacenter IPs hit the same bot wall. A proxy is still required on a server.
  • curl_cffi gives a browser TLS fingerprint. Without it timedtext can return 0 bytes / 429 even through a working residential proxy — an easy misdiagnosis.
  • A JavaScript runtime (Deno by default, or Node via --js-runtimes node) is required by current builds and widens the usable client list.
  • A PO token provider (e.g. bgutil-ytdlp-pot-provider) helps web/mweb clients, but its own docs say a token does not bypass IP-based login restrictions; on datacenter IPs you still need a different exit.
  • Keep one IP per video (sticky sessions) or the media/caption URL can 403 mid-download.
  • Pacing presets: --sleep-requests 0.75 --sleep-subtitles 5 --sleep-interval 10 --max-sleep-interval 20.

4.5 Invidious / Piped public instances free

Public instances expose /api/v1/captions/<id> and similar endpoints, but they are themselves scrapers: instances get blocked, go down, or rate-limit. Treat them as opportunistic best-effort, never as the only path. Self-hosting an instance does not help — it still exits from the same blocked IP unless it is behind a residential connection or proxy.

4.6 Cookies account risk

Authenticating with an account's cookies works for a while but YouTube eventually bans the account, and rotating residential IPs under a signed-in session is itself a bot signal. Use a throwaway account if you must, never a real one. Not a sensible default for a personal knowledge pipeline.

4.7 Audio + local speech-to-text

Robust to missing captions, but the audio download is subject to the same IP wall, so it does not replace a proxy. Cost is local compute (Whisper-class model) and the audio bandwidth through the proxy. Worth keeping as a last resort for videos where no caption track exists at all.

Not a workaround: the official YouTube Data API v3 captions.download endpoint only works for videos the authenticated channel owns or can edit. It cannot fetch arbitrary public captions.

5. Concrete changes for this repo

5.1 One fetcher, a chain of providers

Today fetch_youtube_transcript.py calls YouTubeTranscriptApi() directly and the PHP port tries watch page → Android/iOS/WEB InnerTube → watch-page fallback. Wrap that in a single module with an ordered chain so behaviour is explicit and testable:

  1. Direct — current behaviour, for home/residential runs.
  2. Configured proxy — WebshareProxyConfig if Webshare env vars are set, otherwise GenericProxyConfig with our own retry loop.
  3. yt-dlp — only if installed and the first two raise a block/429; same proxy env var.
  4. Hosted API — only if TRANSCRIPT_API_KEY is set (explicit opt-in).

Make the chain skip a provider whose prerequisite is missing, log which provider answered, and keep the same .transcript / .title output contract so youtube_video_learn.py needs no changes.

5.2 Classify errors before retrying

Retrying a hard IP block is pure latency. Branch on the exception type/message: 

BLOCK_HINTS = ("blocking requests from your ip", "too many requests", "http 429",
               "not a bot", "login_required", "captcha")

def classify(exc: Exception) -> str:
    text = f"{type(exc).__name__}: {exc}".lower()
    if "no english transcript" in text or "transcriptsdisabled" in text:
        return "no_transcript"      # retry elsewhere, do not rotate
    if any(h in text for h in BLOCK_HINTS):
        return "blocked"            # rotate egress / back off hard
    return "transient"              # maybe retry once

5.3 PHP port: proxy + client ladder + pacing

fetch_youtube_transcript.php already rotates ANDROID → IOS → WEB player contexts, which is the right idea. Add:

  • CURLOPT_PROXY / CURLOPT_PROXYUSERPWD from YT_PROXY_URL.
  • Detect playabilityStatus.status and the bot-wall text instead of treating "no caption tracks" as "disabled".
  • A jittered sleep between attempts; do not hammer the same endpoint.
  • Reuse the same proxy exit for the watch-page request and the caption download of a given video (sticky), or the signed caption URL can fail.

5.4 Pacing, caching, and batching

  • Cache first: if .chat/youtube_transcripts/<id>.transcript exists, return it. get_videos_in_playlist.py already skips existing transcripts; mirror that check inside the fetchers so /youtube learn and retries are idempotent.
  • Negative cache: remember videos that genuinely have no English captions so a playlist backfill does not retry them forever.
  • Jitter: sleep 5–20 s between videos in learn_playlist; randomise per request.
  • Batch size: guest sessions are roughly a few hundred requests/hour per IP. A 50-video playlist should be spread over time, not fired at once.
  • Single-flight: the UI's "Learn" button can be clicked twice; a per-video lock (file or in-process) prevents duplicate fetch/rewrite work.

5.5 Observability

Log one line per attempt: video id, provider, proxy label (never credentials), attempt number, elapsed time, error class. Add the canary from section 3 to the learn pipeline's health check. Without this, "YouTube changed something" and "our IP is blocked" look identical in the logs.

6. Code snippets

6.1 Python: proxy config + manual retry (works for any provider)

import os, random, time
from youtube_transcript_api import YouTubeTranscriptApi, RequestBlocked
from youtube_transcript_api.proxies import WebshareProxyConfig, GenericProxyConfig

def make_api():
    user = os.environ.get("WEBSHARE_PROXY_USERNAME")
    pwd  = os.environ.get("WEBSHARE_PROXY_PASSWORD")
    if user and pwd:
        return YouTubeTranscriptApi(
            proxy_config=WebshareProxyConfig(proxy_username=user, proxy_password=pwd)
        )
    url = os.environ.get("YT_PROXY_URL")          # http://user:pass@host:port
    if url:
        return YouTubeTranscriptApi(
            proxy_config=GenericProxyConfig(http_url=url, https_url=url)
        )
    return YouTubeTranscriptApi()

def fetch(video_id: str, tries: int = 5):
    last = None
    for attempt in range(tries):
        api = make_api()          # a new client opens a new connection
        try:
            return api.fetch(video_id, languages=["en", "en-US", "en-GB"])
        except RequestBlocked as exc:   # IpBlocked is a subclass
            last = exc
            time.sleep(min(30, 2 ** attempt) + random.uniform(0, 2))
    raise last
Why a new client per attempt: with a rotating proxy, a kept-alive connection keeps its IP. GenericProxyConfig does not disable keep-alive and has retries_when_blocked=0, so the loop above is what actually rotates the exit. If you switch to Webshare, the built-in retry covers GETs; keep the loop anyway to work around the POST/429 issue described in section 4.2.

6.3 yt-dlp fallback

pip install -U "yt-dlp[default,curl-cffi]"      # curl_cffi fixes empty caption bodies
# Deno or Node must be on PATH for the JS runtime.

yt-dlp --skip-download --write-subs --write-auto-subs \
  --sub-langs "en.*" --sub-format vtt \
  --js-runtimes node \
  --proxy "$YT_PROXY_URL" \
  --sleep-requests 0.75 --sleep-subtitles 5 \
  -o ".chat/youtube_transcripts/%(id)s.%(ext)s" \
  "https://www.youtube.com/watch?v=<video-id>"

6.4 PHP: proxy wiring for the existing fetcher

$proxy = getenv('YT_PROXY_URL') ?: '';
if ($proxy !== '') {
    curl_setopt($curl, CURLOPT_PROXY, $proxy);
    // curl accepts credentials inline in the URL; alternatively:
    // curl_setopt($curl, CURLOPT_PROXYUSERPWD, "$user:$pass");
}
// Keep the same exit for the watch page and the caption download.
// Add a small jitter between client attempts:
usleep(random_int(300_000, 1_200_000));

6.5 Detecting a bot page instead of "captions disabled"

function playabilityStatus(string $htmlBody): string {
    if (preg_match('/"playabilityStatus":\{"status":"([A-Z_]+)"/', $htmlBody, $m)) {
        return $m[1];             // OK, LOGIN_REQUIRED, ERROR, ...
    }
    return 'UNKNOWN';
}
// Treat LOGIN_REQUIRED / "confirm you" / a captcha page as BLOCKED, not as a video without captions.

8. Things that look like fixes but are not

  • Retrying harder from the same IP. A hard block does not expire in minutes, and a 429 on timedtext can persist for hours.
  • Switching library. Python API → yt-dlp → PHP port all exit from the same address. Only the client fingerprint changes.
  • Free proxies / Tor / most VPNs. Their exits are already flagged; Tor is slow and widely blocked.
  • Datacenter proxy pools. They move you off one burned range into another; useful for spreading rate limits, not for the bot wall.
  • Static residential. Same problem as datacenter in practice; the library explicitly warns against it.
  • Fake geo headers. --xff / --geo-bypass are ignored for YouTube; only the actual exit IP matters.
  • Cookies on a real account. Works briefly, risks a permanent ban.
  • IPv6 "millions of IPs" offers. One /64 is one reputation unit.
  • PO tokens alone. Per the provider's own docs, a PO token does not bypass IP-based login restrictions.
