Inside chat.py

Research notes for the interactive, local, lexical RAG chatbot over YouTube transcript trunks. This document traces a question through every stage of retrieval, context construction, prompting, streaming, filtering, and caching, then quantifies the Python-side memory footprint in megabytes.

1. High-level shape

chat.py is a local chatbot over transcript “trunks”: one short paragraph of knowledge per ./youtube_transcript/<video_id>.<index>.trunk file. It deliberately does not use embeddings, cosine similarity, or a vector database. Retrieval is lexical BM25; a small local model expands the query and filters candidates; a larger local model synthesizes the answer.

question
  │
  ├─ optional: Simplified Chinese → English (retrieval only)
  ├─ answer-cache lookup
  ├─ query expansion with qwen3:1.7b
  ├─ BM25 over loaded trunks (question terms ×2 + expansion)
  ├─ fixed top-N by /depth, or adaptive selection (/depth auto)
  ├─ optional qwen3:1.7b relevance filter
  ├─ optional cross-tag fallback when the active scope has no match
  ├─ numbered <chunk id="N"> blocks
  ├─ prompt from research/100_trunks_prompt.txt
  ├─ streaming answer from ornith:35b over Ollama
  ├─ streaming filters remove [Chunk N] and “Supporting Evidence”
  └─ answer stored in cache; sources + metrics kept for commands

Data scopes

Soft tag scope — one global corpus filtered at query time by the tag description and keywords in ./tags.json. Default tag: japan.

Transcript scope — one video selected with /transcript. Tag routing is disabled in this scope.

./tags.json is the tag registry; tags are never written into per-video files.

Three local models

ModelRole
qwen3:1.7bquery expansion, relevance filter, Chinese→English question translation
ornith:35bfinal answer synthesis (streaming)
gemma3:1b/dict definitions

All model weights live in Ollama processes, outside the chatbot’s Python memory.

2. Startup path

  1. parse_args() chat.py:2626 accepts:
    • --tag <tag> (default japan); bare --tag opens an interactive, tab-completed picker.
    • --max-context-tokens N (default 4,096) for adaptive retrieval.
    • --progressive for optional two-pass streaming (off by default).
  2. prewarm() chat.py:2606 runs in a daemon thread and sends a one-token request to qwen3:1.7b and ornith:35b with keep_alive="30m". This moves model loading off the input critical path. Failures are ignored.
  3. load_all_chunks():
    • validates the selected tag against ./tags.json;
    • globs every ./youtube_transcript/*.trunk file into one global corpus;
    • creates lightweight Chunk(video_id, index, trunk_path) objects, sorted by (video_id, index);
    • reads no trunk text and builds no BM25 index yet;
    • /tag thereafter changes only metadata, not the corpus.
  4. Text is loaded lazily through two LRU caches:
    paragraph_text(chunk) — extracts the <paragraph>…</paragraph> body; @lru_cache(maxsize=8192).
    video_title(video_id) — reads <video_id>.title; @lru_cache(maxsize=4096).
  5. PlainFileHistory loads ./.chat/question_history.txt, one entry per line. Questions and slash commands are both saved, so ↑/↓ walks the whole session. prompt_toolkit supplies vi bindings, tab completion, and the toolbar.
  6. The banner prints the loaded-chunk count, tag, default depth, prompt file, and command list. index_memory_report(chunks, build_index=False) reports trunk/video counts and peak RSS; the BM25 index is still lazy.

Why lazy indexing matters: startup only pays for directory scanning and tiny Chunk objects. The expensive tokenized corpus and BM25Okapi structures are created on the first question. /memory before the first question therefore reports “index: built lazily on the first question.”

3.1 Input and command dispatch

session.prompt("You: ") returns a line, stripped of surrounding whitespace. Empty lines are ignored. A line beginning with / is parsed as <name> <argument> and dispatched to the command handler. Otherwise it is a question and goes to answer() chat.py:2279.

Exit aliases are /exit, /quit, /q, and the bare words exit/quit.

3.2 Simplified Chinese detection

contains_simplified_chinese() chat.py:1251 is deliberately lightweight:

  • returns False if the text contains kana (Japanese) or no Han characters;
  • counts characters that occur only in Simplified vs. only in Traditional Chinese;
  • treats shared Han-only text such as 你好 as Simplified.

For a Simplified Chinese question:

  • the question is translated to English with qwen3:1.7b for retrieval only; the prompt tells the model to use standard romanized Japanese place names (e.g. 二条市场 → Nijo Market);
  • answer_language = "Simplified Chinese", which inserts Answer in Simplified Chinese. Do not translate proper nouns. into the final prompt;
  • ornith:35b answers directly in Simplified Chinese. The default path does not translate the answer afterward (translate_answer=False). A streaming Chinese translation path still exists in stream_answer() for callers that request it.

3.3 Answer-cache lookup

make_cache_key() chat.py:2210 includes:

(tag, transcript, depth, max_context_tokens,
 answer_language, progressive, normalize_question(question))

AnswerCache chat.py:411 is a 32-entry LRU of complete answers, each with its source list and estimated context size. On a hit, the cached answer is reprinted, sources are restored, and benchmark stats are filled with zeroes plus cached=True. No retrieval, expansion, filter, or model call occurs.

The cache is cleared by /tag, /refresh, /transcript, /youtube learn, and every /depth change.

3.4 Query expansion

expand_query() chat.py:1346 sends the (possibly translated) question to qwen3:1.7b:

  • asks for 4–8 synonyms / related terms on one line;
  • temperature=0.1, num_predict=32, stop sequences at newline / role labels;
  • strips <think> blocks, removes punctuation, collapses whitespace, caps at 500 characters.

Failure is non-fatal: a warning is printed and retrieval proceeds with the original question only.

3.5 BM25 index construction

get_bm25_index() chat.py:511 builds lazily and caches in _BM25_CACHE (at most two entries, keyed by id(chunks) with an identity check). The two slots let the active-tag index and the cross-tag fallback index coexist.

For each chunk, build_bm25_index() chat.py:496 forms:

document = "<video title>\n<paragraph text>"
tokenized_documents.append(tokenize(document))

tokenize() is a lowercase Unicode word-boundary split with regex \b\w+\b. rank_bm25.BM25Okapi then computes document frequencies, IDF, and document lengths in memory.

3.6 Ranking

top_chunks() chat.py:1173 builds the BM25 query as:

query_tokens = tokenize(question) * 2 + tokenize(expansion)

Duplicating the original question terms makes them outweigh expansion terms. BM25 scores every chunk; non-positive scores are dropped; results are sorted descending. Selection then depends on depth: fixed top-N, or adaptive selection described in section 4.

3.7 Context construction

build_context() chat.py:1211 emits numbered blocks:

<chunk id="1">
[Video: <title>]
<paragraph text>
</chunk>
<chunk id="2">
<paragraph text from a different video: title NOT repeated>
</chunk>
...

The video title is emitted once per video, before its first chunk. Chunk ids are internal metadata; the prompt forbids mentioning them, and streaming filters remove them if the model disobeys. Unreadable paragraphs are skipped, and ids advance only for emitted chunks.

estimate_tokens() chat.py:1239 is a cheap approximation: ceil(ASCII_chars / 4) + non_ASCII_chars. It powers the context-size line and the adaptive budget, not billing.

After selection the chatbot prints:

[using N of M BM25 trunk(s) (depth D, default/explicit)]
[context size: ~T token(s) estimated across N trunk(s);
 context window: 32,768 token(s)]

In adaptive mode the first line becomes [auto retrieval: …].

3.8 Prompt construction

build_prompt() chat.py:2230 loads research/100_trunks_prompt.txt (or a built-in equivalent). It:

  • replaces the template’s <context>…</context> block with the numbered chunk blocks;
  • replaces [Insert your question here] with the question;
  • changes “the 100 chunks” to the actual chunk count when present;
  • injects the language instruction immediately before ### TARGET QUESTION: when needed;
  • prepends prompt_prefix if supplied.

The template enforces grounding in the provided chunks, no chunk citations, conflict disclosure, deduplication for counts, and an exact missing-data sentence. It asks for a direct synthesis with no separate evidence section.

3.9 Answer generation and streaming

stream_answer() chat.py:1609 POSTs to Ollama’s /api/generate with:

ParameterValue

keep_alive30m

Each NDJSON line is parsed and its response token passes through two stateful streaming filters:

ChunkCitationFilter

Removes [Chunk 11], [Chunks 11, 14], [chunk #3], including partial citations split across tokens. It holds ambiguous [ prefixes until they can be resolved, and trims whitespace that would otherwise be duplicated.

SupportingEvidenceFilter

Suppresses a trailing “Supporting Evidence” section, including Markdown headings, bold markers, bullets, and blockquotes, even when the heading is split across tokens. The same section is stripped again from the final string.

The full English answer is accumulated and returned. If translation is requested, sentence/line groups are translated on the fly by qwen3:1.7b and printed in Simplified Chinese; list markers are restored if the small model drops them. The default chatbot path does not enable this because it asks ornith:35b to answer in Chinese directly.

Ollama’s final event supplies load_duration, prompt_eval_count, prompt_eval_cached_count, prompt_eval_duration, eval_count, and eval_duration. The first displayed token time is recorded as request TTFT. End-to-end TTFT is retrieval time + request TTFT.

3.10 Optional progressive mode

With --progressive, if more than 10 chunks were selected, the first 10 are streamed in one call. A second call receives the remaining chunks and the answer so far, with instructions to add only missing details without repetition. The two responses are concatenated. This trades a little coherence for a faster first token and is off by default. The progressive flag is part of the answer-cache key.

3.11 Post-processing, caching, metrics

The returned answer passes once more through strip_chunk_citations() and strip_supporting_evidence(). It is stored with its selected (chunk, BM25 score) sources and estimated context tokens. The latest answer, sources, and benchmark stats are retained for /dict, /sources, and /benchmark.

No metrics line is printed by default. With /benchmark (or /benchmark on), format_benchmark_line() prints retrieval, expansion, BM25, filter, context build, prompt build, prefill, model load, TTFT, prompt tokens (and cached tokens), estimated context tokens, and total time.

4. BM25 retrieval and chunk selection

4.1 Fixed depth (default)

DEFAULT_DEPTH = 20. /depth <n> changes the number of top-scoring chunks. Only chunks with a positive BM25 score are eligible. There is no score threshold beyond > 0 in fixed mode.

4.2 Adaptive depth (/depth auto)

_select_auto_chunks() chat.py:1097 applies deterministic rules. It makes no extra model call:

  1. Candidate cap. Consider at most AUTO_CANDIDATE_LIMIT = 50 ranked chunks.
  2. Minimum context. Always keep at least min(FALLBACK_TOP_N = 10, available) chunks.
  3. Score elbow. After the minimum, stop when a score is below 15% of the best score (SCORE_FLOOR_RATIO) or drops more than 35% from the previous score (SCORE_ELBOW_RATIO).
  4. Per-video diversity. At most MAX_CHUNKS_PER_VIDEO = 5 chunks from one video.
  5. Near-duplicate removal. Drop a chunk if the Jaccard overlap of its token set with an already-selected chunk is ≥ 0.90 (NEAR_DUPLICATE_JACCARD).
  6. Token budget. Stop at MAX_CONTEXT_TOKENS = 4,096 estimated tokens by default; list/aggregation questions get LIST_CONTEXT_TOKENS = 6,144. A chunk costs estimate_tokens(paragraph) + 16.
  7. Never empty. If every rule filtered everything out, keep the single best chunk.

List/aggregation detection uses LIST_QUERY_PATTERN: list, all, every, each, compare, comparison, detail(s), detailed, enumerate, options, type(s), kind(s), level(s), example(s), recommendation(s). Such questions skip the relevance filter (to preserve breadth) and receive the larger adaptive budget.

5. Small-LLM relevance filter and cross-tag fallback

5.1 When the filter runs

filter_candidates() chat.py:1360 runs only when all of these hold:

  • LLM_FILTER_ENABLED is true (it is);
  • the question is not a list/aggregation question;
  • 5 ≤ candidate count ≤ 20 (FILTER_MIN_CANDIDATES / FILTER_MAX_CANDIDATES).

Fewer than 5 candidates are returned unchanged. More than 20 are not filtered because the prompt would become too large and the filter’s precision benefit drops.

5.2 Filter prompt and parsing

The filter prompt lists each candidate number plus a snippet capped at 700 characters (FILTER_SNIPPET_CHARS). qwen3:1.7b must return a comma-separated list of useful candidate numbers, or exactly NONE. The call uses temperature=0, num_predict=96, and stops at a blank line.

  • Parsed list → keep only those candidates.
  • NONE → candidate set treated as empty; soft-tag routing may run.
  • Unparseable / request failure → question filter reported as skipped; unfiltered BM25 candidates are kept. The separate tag-scope filter has its own status and lexical fallback.

5.3 Soft-tag routing

Tags no longer partition the corpus. After question retrieval, tag_filter_candidates() asks qwen3:1.7b to keep only candidates relevant to both the active tag (name, description, keywords) and the question. If the tag filter returns NONE, the CLI/server ranks the other registry tags from the same candidate set using lexical tag profiles and re-runs retrieval for the best tag(s), switching only after a scoped answer succeeds. If no tag fits, the chatbot explains the scope instead of silently citing unrelated chunks. Fallback is disabled for explicit /transcript and /article scopes.

Filter safety net: if the filter returns nothing but BM25 did return candidates, answer() keeps the best FILTER_MIN_KEEP = 3 unfiltered candidates rather than refusing to answer.

8.5 Why memory stays moderate

  • No embeddings and no cosine-similarity matrix: memory scales with total tokens, not with an embedding dimension.
  • Trunk text is read lazily; the Chunk object stores only a path.
  • One BM25 index per active scope, with at most two cached indexes.
  • Cross-tag data is lazy and invalidated by tag-file mtime.
  • The answer cache is bounded to 32 entries.
  • The paragraph and title LRUs are bounded at 8,192 and 4,096 entries.
  • Model weights live in Ollama, not in the chatbot process.

/memory calls index_memory_report(chunks), which reports trunk/video counts, BM25 tokenized-term count, and process peak RSS. It does not report Ollama’s RSS or model-weight memory.

11. Failure behavior and safety nets

  • Ollama unreachable: generation raises RuntimeError; main() prints Error: … and keeps the session alive.
  • Query expansion failure: warning; retrieval uses the original question only.
  • Filter failure / unparseable output: keep unfiltered BM25 candidates.
  • Filter returns NONE: try cross-tag fallback unless in transcript scope; if still empty, keep the top 3 BM25 candidates rather than refuse.
  • No trunks in scope: load_chunks() exits with a hint to run youtube_video_learn.py.
  • Trunk read failure during context build: that chunk is skipped; if no text remains, answer() reports that it could not read matching contents.
  • Model leaks chunk citations or a Supporting Evidence section: streaming filters and a final post-pass remove them.
  • Stale cached answer: the cache key includes tag, transcript, depth, token budget, language, progressive flag, and normalized question, so configuration or scope changes cannot reuse an old answer.
