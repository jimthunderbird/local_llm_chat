Research / architecture note

Project Gutenberg Book-Specific Chat

How the /gutenberg book reader answers questions about a single book: a section-aware, content-addressed, lexical RAG pipeline built on the existing /article engine, isolated per book and streamed into a two-column modal.

Scope: current implementation in app/chat_server.py and app/chat.html, reusing chat.py. Based on source inspection plus the books already cached under .chat/gutenberg_cache.

01Executive summary

The book-specific chat is not a separate RAG stack and it does not put a whole book into the model context. It is an isolated instance of the existing article pipeline:

  • One book = one isolated ChatState. The main chat's tag/transcript scope and conversation are untouched while the modal is open. Up to three book sessions stay resident; older ones are evicted, while their downloaded text and on-disk index stay cached.
  • Paragraph-level lexical retrieval. The cleaned book is split into article-style paragraph trunks. BM25 over those paragraphs is the retrieval source of truth. There are no embeddings and no cosine similarity.
  • A deterministic summary tree adds document structure. A cached structure file records chapter/section spans and builds extractive section summaries, a compact overview, and a larger digest. Those synthetic trunks are attached only when useful; they never replace paragraph retrieval.
  • Routing chooses the cheapest context shape. A question is routed to one of: whole-book overview, one section, narrow retrieval, or iterative evidence gathering across the book.
  • Small-model evidence checks bound the context. The iterative path retrieves a few paragraphs at a time and asks qwen3:1.7b whether the evidence is sufficient, adding missing terms to the next BM25 query. Hard round and token caps guarantee termination.
  • The answer is streamed by ornith-1.5:35b. The prompt is the existing file-based 100-trunk prompt template, with article-specific instructions prepended. Answers stream over SSE into a per-book chat pane, and every word remains dictionary-clickable.
The core idea: classify the question first, retrieve only the paragraphs (and a few section summaries) needed for that kind of question, then answer inside a bounded 32,768-token model window. A multi-megabyte novel is never copied into the prompt.

The two columns are intentionally decoupled. The left pane is a pure plaintext read; the right pane owns the retrieval and model work. A book is indexed lazily on the first question, not when the modal opens, so opening a book costs only the plaintext download.

03Catalog search

/gutenberg search <keywords> is implemented by search_gutenberg_books(). It returns up to GUTENBERG_BOOK_RESULT_LIMIT = 12 normalized cards.

  1. Open Library first. A free-form query such as the time machine by h g wells is parsed into the documented ?title=…&author=… form; other queries use q. The response is requested with id_project_gutenberg, cover_i, cover_edition_key, edition_count, ebook_access and related metadata. Each work that has a numeric id_project_gutenberg becomes a card.
  2. Gutenberg catalogue fallback. Not every Open Library work is linked to a Gutenberg text yet. If fewer than 12 cards are found, the gutenberg.org/ebooks/search/ page is parsed for ebook ids, titles, authors, and download counts. It only fills the remaining slots.
  3. Deduplication. Results are deduplicated by canonical numeric Gutenberg id, so the same book cannot appear twice from the two sources.

A card carries id, title, authors, languages, subjects, first_publish_year, download_count, the gutenberg.org/ebooks/<id> page URL, and the plaintext URL …/ebooks/<id>.txt.utf-8. The server emits these as a books SSE event; the browser renders clickable cards.

04Book ingestion and caching

ensure_gutenberg_book(book_id, text_url, title) owns download and normalization. It is idempotent and safe under concurrent requests: per-book locks make sure two tabs cannot download and write the same book at once.

Download policy

  • Validate the id with ^\d{1,8}$.
  • Reuse .chat/gutenberg_cache/<id>.txt and <id>.rag.txt if both exist.
  • Stream the download in 256 KiB blocks.
  • Reject books over GUTENBERG_TEXT_MAX_BYTES = 30 MiB.
  • Write to temporary files, then atomically rename.

Normalization

  • Decode UTF-16 when a BOM is present, then try UTF-8 BOM, UTF-8, CP1252, Latin-1, and finally UTF-8 with replacement.
  • Strip the Project Gutenberg *** START OF … *** and *** END OF … *** boilerplate.
  • Remove the older “End of Project Gutenberg” trailer.
  • Store clean text as <id>.txt.

Why there are two files

<id>.txt is the human-readable book shown in the left pane. <id>.rag.txt is the RAG-friendly copy:

  • Lines matching CHAPTER|BOOK|PART|VOLUME|ACT|SCENE (roman|digits) … are promoted to Markdown ## headings, so the article structure builder can create chapter/section spans and summaries.
  • The title is prepended as # Title if it is not already near the top, so broad overview questions retrieve a useful document heading.
Known normalization limit: only the chapter conventions in the regex are promoted. Gutenberg editions that use headings such as I., II., or plain titles without CHAPTER may collapse into a single section. Retrieval still works at paragraph level; only the parent-summary and section route become coarser.

05The book-specific index

On the first question, _load_article_chunks(rag_path) turns the RAG text into an article-style trunk set. The index is content-addressed: a SHA-1 of the absolute path plus the file bytes yields article_<16 hex chars>, and everything lives under app/.article_cache/article_<hash>/. Changing the book bytes creates a new cache entry instead of silently reusing stale metadata.

Trunk layout

Trunk indexKindContentsUsed for
0 Overview Title, compact outline, TL;DR/summary section (or opening paragraphs) Concise “what is this book about?” questions
-1 Digest Overview plus representative content from every major section, capped at 16,000 characters Long-form overview requests (“in 1000 words”, detailed summary)
-101, -102, … Section summary Deterministic extractive summary of one section, up to 1,400 characters Parent context for retrieved paragraphs; not normal BM25 input
1, 2, 3, … Paragraph One book paragraph wrapped in <article><title>…<paragraph>… The retrieval source of truth

Section summaries use index ARTICLE_SECTION_SUMMARY_INDEX_BASE - section_number (-100 - n). Negative indexes keep synthetic trunks out of ordinary BM25 retrieval; paragraph chunks (index > 0) are the only documents indexed by _iterative_paragraph_chunks().

Structure builder

_article_build_structure() persists article_structure.json with a schema version (ARTICLE_META_VERSION = 4), the book title, headings, overview, digest, sections, and a paragraph map. The map records, for every paragraph, its nearest preceding heading, section number, and section start/end.

  • Headings come from HTML <h1>–<h6> (for articles) and Markdown headings (for Gutenberg chapters). Markdown headings retain ## in paragraph text, so the section map compares both spellings.
  • Section assignment uses the nearest preceding heading. Numbered headings (1., 2.3) are accepted as a fallback when markup is absent. Text before the first heading becomes an “Introduction” section.
  • Section summaries are extractive, not model-generated: take the first substantive paragraphs in the span, skip heading-shaped and tiny navigation fragments, and cap at 1,400 characters. This is fast, deterministic, cacheable, and cannot hallucinate.
  • Overview = title + outline (up to 1,400 characters) + TL;DR/summary section (up to 2,400 characters), falling back to the opening substantive paragraphs.
  • Digest = the overview plus the first content from each top-level section, with a 16,000-character cap. It exists because a 1,000-word overview request needs more than a table of contents and a TL;DR.

Runtime-only indexes (_section_lookup, _paragraph_lookup) are attached after loading and are not persisted.

06Question routing

A book session sets article_path and article_iterative = True. That puts _run_question() into article mode and bypasses normal tag routing and cross-tag fallback. Every question is routed by article_question_route() into one of four shapes:

RouteHow it is chosenContext shape
Overview Broad-overview regex, or an overview intent plus a document reference / bare deictic (“what is this about, in 1000 words”). Use chunk -1 (digest) when a word count or detailed request is present; otherwise chunk 0 (overview). BM25 is skipped.
Section Question tokens match a section heading (substring or ≥60% heading token coverage), and the question is not enumerative. Restrict candidates to that section's paragraph span; depth 12, budget 8,192 tokens; attach the section summary and one-paragraph neighbors.
Narrow Default when the question is a specific fact and no section confidently matches. Iterative evidence because article_iterative is on; otherwise BM25 depth 20 with budget 6,144 tokens and parent/neighbor expansion.
Iterative Enumerative/comparative regex, or the configured article default. Also chosen when section intent exists but no heading match is found and the small router says NARROW. Up to 4 rounds × 4 new paragraphs, 50 BM25 candidates per round, 16,000 token cap, plus one parent summary per represented section.

Small-model fallback router

If a question looks section-oriented (for example “explain the workflow …”) but no heading matches, _article_classify_with_model() asks qwen3:1.7b to reply with exactly one of OVERVIEW, SECTION <n>, or NARROW. The model sees a numbered list of up to 80 section headings (160 characters each) and the question, with num_predict=32. A failed, malformed, or missing response falls back to the ordinary regex route, so the model can improve routing but cannot break it.

Routing is deliberately cheap and conservative. Regex rules handle the obvious cases; the small model is consulted only for ambiguous section-intent questions. The route determines the context budget before any answer model work begins.

07Retrieval and evidence gathering

BM25 over paragraph trunks

chat.top_chunks() builds or reuses a cached BM25Index for the book's paragraph list. Each document is the paragraph text prefixed with the book title. Retrieval is lexical, not vector-based.

  • Tokenizer: lowercase \b\w+\b tokens with conservative plural/inflection folding (for example books → book) and compact time expressions (3 a.m. → 3am).
  • Query weighting: original question tokens ×2, fuzzy out-of-vocabulary corrections ×2, acronym expansions ×2, and validated small-model expansion terms ×1.
  • Fuzzy correction: words missing from the index vocabulary are matched against same-first-letter, similar-length vocabulary words by string similarity plus co-occurrence with other query anchors. This handles misspelled names and places without changing correctly spelled words.
  • Acronym expansion: for an acronym in the question, the corpus is mined for a nearby definition such as “International Driving Permit (IDP)” and the full form is added to the query.
  • Entity focus: when the question contains a named entity, candidates are softly constrained to chunks mentioning that entity (and preferably its topic words). If no chunk matches, the constraint is dropped rather than returning an empty result.
  • Query expansion: qwen3:1.7b proposes search terms, but expansion terms are validated against the corpus. A term is kept only when enough documents containing it also contain a distinctive anchor from the original question, preventing model drift.
  • Selection: explicit depth returns the top N; adaptive retrieval applies a score elbow, a score floor, a per-video/per-book chunk cap, near-duplicate Jaccard removal, and a token budget.

Small-model relevance filter

When there are 5–20 candidates and the question is not a list/aggregation question, filter_candidates() asks qwen3:1.7b which candidates are relevant. The filter is bounded and never allowed to destroy the strongest lexical evidence: the top BM25 candidates are always kept, and if the filter rejects everything, retrieval keeps the top five instead of producing a false refusal.

The iterative evidence loop

_article_iterative_evidence() delegates to _iterative_evidence(). This is the book chat's most important algorithm:

  1. Expand the question once (cached), then BM25-rank up to 50 paragraph candidates against the whole book.
  2. Add new paragraphs: 8 in round 1 (batch × 2), then 4 per round, skipping already-seen chunks and respecting the token budget.
  3. Fast path: if the evidence already contains every content word of the question, and the question is not enumerative, stop without a model call.
  4. Otherwise ask qwen3:1.7b with ARTICLE_SUFFICIENCY_PROMPT: VERDICT: YES/NO, supporting excerpt number, and MISSING: terms. Excerpt text is capped at 6,000 characters.
  5. If sufficient, stop. If not, append the reported missing terms to the next BM25 query. Stop early if the missing terms do not change, if no new candidates appear, after 4 rounds, or at the token cap.
  6. In article mode, add one parent section summary for every section represented in the evidence, then return the final context in document order. 
for round in 1..4:
    rank = BM25(search_question, paragraph_chunks, limit=50)
    add up to 8 (first round) or 4 new paragraphs within budget
    if evidence covers every question term: stop
    verdict = qwen3:1.7b.sufficiency(question, evidence)
    if verdict.sufficient: stop
    if verdict.missing unchanged: stop
    search_question += verdict.missing

attach one section summary per represented section
sort by document order; enforce the final token cap

This loop is what makes a narrow factual question cheap: it usually stops after one small batch. A broad “list every …” question keeps gathering until it hits the round or token cap. The cap is a safety property, not a target.

The evidence budget for the iterative book route is 16,000 estimated tokens, but the actual context is usually much smaller because only a few paragraphs are added per round. For example, the cached Time Machine has ~38,145 tokens across 584 paragraphs, so a typical 4-round run selects roughly a few thousand tokens, not the whole book.

Narrow and section expansion

When the route is narrow (iterative disabled) or section, _make_article_expansion() adds context before prompting:

  • Parent section summaries for the strongest four selected paragraphs.
  • One neighboring paragraph on each side, only within the same section.
  • Strict token budgeting; if expansion would exceed the budget, the original selection is kept.

Section mode additionally restricts the candidate pool to the section's paragraph span and uses depth 12 / 8,192 tokens. This is the most focused context shape.

08Prompting and answer streaming

chat.answer() builds numbered <chunk id="…"> blocks with the book title emitted once per source, then fills research/100_trunks_prompt.txt. The template enforces grounding in the provided chunks, forbids citing chunk ids, asks for conflict disclosure and deduplicated aggregation, and defines the missing-data response. Article mode prepends a route-specific prefix:

PrefixInstruction
### ARTICLE OVERVIEW Use the title/outline/summary or digest; honor requested length; answer from the whole-document context; omit unsupported details rather than refusing.
### ARTICLE SECTION Prefer specific paragraphs for facts and use the section summary for orientation; ground every claim.
### ARTICLE EVIDENCE Evidence was gathered across the whole book in rounds and document order; answer every part, including lists and comparisons; do not claim insufficiency.
### ARTICLE CONTEXT Narrow retrieval with parent summaries and neighbors; use summaries for orientation only.

Answer model

ornith-1.5:35b, thinking disabled, requested context window ANSWER_NUM_CTX = 32,768 tokens, streamed token by token.

Small helper model

qwen3:1.7b at 8,192 tokens for query expansion, relevance filtering, sufficiency checks, and article/section routing. Keeping the same context size avoids Ollama reloads.

Streaming uses SSE. The browser handles meta, delta, reset, error, and done events. The server strips chunk citations and supporting-evidence headings before the final answer is saved or returned, keeping internal retrieval metadata out of the UI.

After the answer completes, the server sends the session snapshot and, in benchmark mode, the retrieval/prefill/TTFT line. In normal mode those diagnostics stay out of the answer.

09Session isolation, history, and cache

One session per book

get_gutenberg_chat_state(book_id) returns a dedicated ChatState with:

  • chunks and global_chunks set to the book's trunks only,
  • article_path set to the cached .rag.txt,
  • article_structure set to the summary tree,
  • article_iterative = True,
  • its own conversation, answer cache, latest answer, sources, and benchmark state.

The handler temporarily swaps self.state to the book session, runs the normal question pipeline, and restores the previous state in a finally block. The main chat is therefore unaffected, and book A cannot see book B's text. The neutral default tag is used, but article mode overrides tag routing, so the book never falls back to another tag or to the global transcript corpus.

LRU eviction, persistent disk state

GUTENBERG_BOOK_STATE_LIMIT = 3. Each access moves the book to the end of an LRU order; exceeding three resident sessions evicts the oldest and calls gc.collect(). Eviction only drops the in-memory ChatState. The downloaded plaintext, .rag.txt, and .article_cache index stay on disk, so reopening a book is a cache hit rather than a re-download or re-split.

Conversation and cache semantics

  • Follow-ups: when a question contains context-dependent references, resolve_question() asks the conversation model (ministral-3:3b) to rewrite it into a standalone question using up to the last 8 turns. The rewritten question is used for retrieval; the original question is shown in the UI.
  • Answer cache: each session has a 32-entry LRU. The key includes the tag/scope, transcript, depth, context budget, answer language, question, tags version, model, and, in article mode, the article path, structure id, and iterative flag. Context-sensitive questions add the conversation revision, so “what does he think?” cannot reuse an answer cached for a different “he”.
  • Reset: the first question sent after opening the modal carries reset: true; the server clears that book's conversation, answer cache, and latest answer/sources. Later questions in the same modal keep the thread.
  • Concurrency: each session has an RLock, so two questions cannot mutate one book's conversation or cache simultaneously.

Why this is memory-efficient

The model never sees the full book. Retrieval selects paragraphs first, and only those paragraphs plus a small number of extractive section summaries reach the prompt. Even the largest locally cached example (60 years of best sellers, 5,536 paragraphs) contributes a bounded digest or a small evidence set, not 482k characters of book text.

The in-memory footprint is dominated by the BM25 index, not the model context. A rough order-of-magnitude measurement from the cached trunks:

Book indexParagraphsTokensVocabularyRough index memory
The Time Machine584~38k~4.3k ~3 MB (token lists/strings + vocab + document frequencies)
60 years of best sellers5,536~149k~7.8k ~10–12 MB

These are estimates from tokenizing the cached trunks; actual BM25 counters add some overhead. They still show that three resident book indexes are small compared with the 35B answer model itself.

Latency profile

  • Modal open: one plaintext cache read and a JSON response. Indexing is deferred until the first question.
  • First question: download if necessary, paragraph split, structure load/build, BM25 build. The structure is cached on disk, so later opens skip the expensive split.
  • Later questions: reuse the cached BM25 index and structure. The iterative loop's dominant extra cost is the small-model sufficiency call, which is skipped when the evidence already contains every question term.
  • Answer time: dominated by ornith-1.5:35b generation. Retrieval is lexical and local.

11Browser UI behavior

Two-column modal

  • Centered overlay; left pane is the cached plaintext, right pane is the per-book chat.
  • Header shows title, authors, languages, and download count, plus an “Open on Gutenberg ↗” link.
  • Escape closes the modal, but smaller overlays (dictionary, line help, help) get Escape first.
  • Clicking the backdrop closes it.

Plaintext word lookup

  • The book stays one text node, avoiding millions of DOM nodes for a large novel.
  • Pointer-to-caret mapping finds the word under the cursor and walks only that word's boundaries.
  • Hover uses the CSS Custom Highlight API; dragging to select text does not trigger a lookup.
  • Clicking sends the word plus a ~900-character surrounding excerpt to the streaming /api/dict popup.

Per-book chat

  • Enter sends; Shift+Enter inserts a newline.
  • SSE deltas render Markdown progressively with a “thinking…” state.
  • Generation counters and AbortController discard stale responses when the book changes or the modal closes.
  • Every word in the answer opens the same dictionary popup used by the main chat; selecting text is never treated as a word click.
  • The chat scrolls to the latest content while streaming.

Search cards

  • Book results are rendered as a responsive card grid.
  • Each card shows title, authors, and metadata; clicking it opens the reader modal immediately.
  • The left pane shows the plaintext character count; errors are shown inline.

12Design limits and failure modes

SituationBehavior
Open Library has no Gutenberg id for a work Fall back to the Gutenberg catalogue search page for the remaining slots.
Book has no plaintext edition or download fails Return a JSON error / SSE error; the left pane shows the failure instead of hanging.
Book is larger than 30 MiB Refuse to cache it and report the limit.
Chapter headings do not match the promotion regex The book may become one section; paragraph retrieval still works, but section routing and parent summaries are coarser.
No paragraph matches a question Return no evidence rather than fabricating context; the UI receives an error or an empty answer path.
Small model unavailable or returns malformed JSON/text Routing and sufficiency checks fall back to regex/lexical behavior; retrieval still runs.
More than three books open over time The oldest in-memory session is evicted; disk caches remain.
Two simultaneous questions for one book Serialized by the session lock; the UI also blocks a second send while busy.
No embeddings, by design. The book chat inherits the project's lexical BM25 architecture. This keeps indexing cheap and explainable, but it also means exact wording and normalization matter: synonyms not present in the book will not match unless query expansion or fuzzy correction bridges them. The small-model expansion/filter steps are the mitigation, not a semantic vector index.
